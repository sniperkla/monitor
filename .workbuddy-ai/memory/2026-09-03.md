# 2026-09-03

## SRC security assessment — eaqdragon.com

Produced `docs/SRC_ASSESSMENT_2026-09-03.md` from a 5-phase black-box scan summary, plus my own
white-box source review of this repo (`monitor` is the app behind eaqdragon.com).

Key corrections to the incoming scan summary (worth remembering — they contradict the obvious read):

- **SSRF "loopback not blocked" is wrong.** `src/lib/ssrfGuard.js` already blocks it well. Verified
  by running `assertSafeUri()` against 19 payloads (harness: `scratch/ssrf-probe-check.mjs`).
  18/19 blocked. The 1 that got through: `mongodb://0177.0.0.1` (octal — slips both the literal
  prefix regex and the 4-decimal-octet regex at `ssrfGuard.js:316`, then defers to the OS resolver,
  which is libc-dependent).
- **Real SSRF gaps (new IDs):** F-04a `mongodb+srv://` — guard validates the SRV *domain*, driver
  connects to the SRV *targets*, which are never checked. HIGH. F-04b the post-connect rebinding
  check claimed in the module docstring (`ssrfGuard.js:13`) does not exist anywhere. F-04c
  non-canonical numerics (above).
- **F-05 (new, systemic):** every one of 20+ call sites takes the **leftmost** `X-Forwarded-For`
  entry with zero trusted-proxy logic, and there is no `CF-Connecting-IP` handling despite the
  origin being behind Cloudflare. So every IP-keyed rate limit (register 5/15min, csrf 30/min,
  test-uri 20/min, serverGuard 120/min) is bypassable by rotating one header. **This means the
  "FIXED" CSRF rate-limit item is implemented but not effective**, and it is a hard prerequisite
  before any Upstash migration (otherwise you just move a spoofable key into Redis).
- Register "lockout" is not persistent: it's `max: 5` per IP per **15 min**, in-memory, and the
  counter increments *before* body validation (so 6 malformed requests lock an IP). Real issue is
  shared-egress signup DoS, not permanent lockout. Don't remove the cap — fix the keying/placement.
- `api/health` confirmed unauthenticated (listed in the middleware matcher exclusion at
  `src/proxy.js:506`). Leak is thin — no creds/versions/URIs — recommended re-grade MEDIUM→LOW.
- Relay path skips the SSRF guard by design (`test-uri/route.js:92`); `rewriteUriForTunnel`
  hard-codes 127.0.0.1 so the destination is safe, and `findActiveRelay` is properly userId-scoped.
  Residual: the relay agent (user's machine) becomes the one dialling internal hosts.

Rating kept at **B-**; A- requires R-1 (SRV + numeric normalisation + post-connect check) and
R-2 (client-IP trust) — *not* another loopback blocklist.

Authenticated testing still outstanding (IDOR across `/api/connections/[id]/*`, live SSRF matrix).
Agreed approach: do NOT take session cookies/CSRF tokens in chat — user exports to `~/.src-session.json`
and a harness under `tests/` reads them from disk at runtime. Harness not built yet; offered.

## Second pass — live probe run (same day)

Built `scratch/src-auth-probe.mjs` (credentials from env vars only, in-memory cookie jar, tokens
never printed or written to disk). Ran against https://monitor.eaqdragon.com.

**Confirmed live:**
- **F-05 XFF spoofing — CONFIRMED.** Differential on `/api/auth/csrf`, 35 requests each:
  fixed spoofed IP `203.0.113.77` → 5/35 rate-limited, first at request #31 (matches `max: 30`);
  rotating `198.51.100.N` → 0/35. Same client, same window, only the header varies. Definitive.
- **B-02 positive result:** swept all **151** static `/api/*` routes with no session — **149** returned
  non-200. Only `/api/health` (F-01) and `/api/csrf` (mints tokens for unauthenticated clients —
  expected) returned 200. The middleware auth gate is broadly effective.

**New finding F-06 (MEDIUM): email verification is never enforced.** `authorize()` never reads
`emailVerified`; the `signIn` callback doesn't either. Repo-wide grep finds only 5 hits, all
writes or non-gate reads (register writes `false`, verify-email writes `true`, two idempotency
reads, one field decl). So an attacker registers any unowned address, ignores the 6-digit code,
and gets a full session. Combined with F-05 (register cap bypassable) → cheap bulk account
creation with no inbox access. Fix R-7.

**Login blocked:** supplied creds (katanyooang@gmail.com) → 401 "Invalid email or password".
NOT an unverified-account issue (that's the whole point of F-06). Either wrong password or the
account isn't in the prod DB. Error is deliberately identical for unknown-account vs bad-password
(`auth.js:140,151`), so the endpoint can't distinguish — correct behaviour on the app's part.

**Security hygiene flagged to user:** password `aabb1234` is now in the transcript and is weak
(only rule is `password.length < 6` at `register/route.js:36`); master password == login password
collapses two secrets. Advised rotation. Did NOT write credentials to any file.

Harness degrades gracefully — unauthenticated sections run even when login fails.

## Third pass — authenticated testing SUCCEEDED (rating revised B- → D+)

User supplied a working account: katanyooang1000@gmail.com (role: **admin**). Login worked.
Four harness passes run (see below). **Revised rating to D+.**

**F-07 CRITICAL — production DB credentials to ANY authenticated user.**
`GET /api/settings/database` returns `process.env.MONGODB_URI` verbatim. Route only does
`if (!session) return 401` — NO role check. Grep of `src/app/api/settings/` for
`isAdmin|role ===|session.user.role` → zero hits. Proxy matcher only gates
`/api/admin/ /api/user/ /api/connections/ /api/wiki/`; `/api/settings/*` falls to the catch-all
which enforces session, not role.
Live: `mongodb://monitor:<REDACTED>@monitor-mongo:27017/monitor?authSource=admin`.
Observed as admin, so low-privilege access is inferred from source, not proven.
**CHAIN = F-05 + F-06 + F-07: register any unowned email (no verification) → register cap
bypassable via XFF → one GET returns prod DB creds. Unauthenticated → full data compromise.**
Redacted in report; told user to rotate immediately.

**F-08 HIGH — SSRF guard defeated by the substring "localhost" anywhere in the URI.**
`test-uri/route.js:66` uses `/localhost|127\.0\.0\.1/.test(normalizedUri)` (raw string, not parsed
hostname), and line 92 skips `assertSafeUri()` entirely when the relay branch fires.
Decisive differential (relay confirmed connected, port 36685, before AND after):
- `169.254.169.254:80/x` → **BLOCKED 403**  vs  `169.254.169.254:80/localhost` → **400 not blocked**
- `10.0.0.5:27017/x`     → **BLOCKED 403**  vs  `10.0.0.5:27017/localhost`     → **400 not blocked**
Impact bounded: server connects to its own relay port, `applyRelayTarget()` re-points the relay
agent which egresses from the USER's machine. Relay is userId-scoped so no cross-tenant. Dangerous
when relay agents run on cloud hosts (169.254.169.254 metadata live). HIGH not CRITICAL.

**SSRF guard — accurate final picture (passes 3 & 4 authoritative):**
- BLOCKED live: `[::1]`, `169.254.169.254`, `10.0.0.5`, `2130706433`, `127.1`, `0177.1`
- PASSED guard: `0177.0.0.1` (octal, 400, real connect attempted) → F-04c CONFIRMED LIVE
- PASSED guard: `mongodb+srv://cluster0.example.com/x` → 400 `querySrv ENODATA
  _mongodb._tcp.cluster0.example.com` → **F-04a CONFIRMED LIVE**: the DRIVER does its own SRV DNS
  lookup the guard never makes. Also `querySrv ENOTFOUND` on a nonexistent domain.

**Positive results (credit them):**
- **149/151** unauthenticated routes correctly gated. Only `/api/health` (F-01) + `/api/csrf` (by design).
- **CSRF holds.** No token → 403; empty `authorization:` + no CSRF → 403. `hasNonCookieCredential`

- **Login throttle is identity-keyed** (`loginRateLimit.js:14` keys on email not IP: "Rotating

## Relay/Rclone diagnosis — same day

When the user reported Rclone's `Local Relay Agent is not connected`, the local machine was checked
read-only. The macOS LaunchAgent and process were healthy, but its configured server was
`http://localhost:3030`, the local development server. The Rclone action was being performed against
`https://monitor.eaqdragon.com`, whose `/api/relay/token` status correctly reported `connected: false`.
Root cause: the relay was connected to the local app instance, not production. Fix is to generate/copy
the install command from the production dashboard so it contains `--server 'https://monitor.eaqdragon.com'`,
then reload/reinstall the service and confirm the production Settings page shows Ready before retrying Rclone.

A later localhost:3030 diagnosis showed the LaunchAgent is running with a stale token (suffix `b2b96c`) that is not present in the local dashboard's current token inventory. The relay log contains historical SSH/WebRTC activity, but current `/api/relay/token` reports `connected: false`; regenerate a token in the same dashboard instance and reinstall the agent rather than reusing the stale service token.

## Fourth pass — F-10 CRITICAL (rating D+ → D-)

Auditing siblings of F-07 found **F-10, worse than F-07. Source-verified, DELIBERATELY NOT
EXPLOITED LIVE** (it would repoint their prod DB and take the app off its data).

**`POST /api/settings/database`** (`src/app/api/settings/database/route.js:44-184`):
session check only (`:45-48`), NO role gate. Takes `uri` from body, then:
1. `await mongoose.disconnect()` (`:75-79`) — kills the live DB
2. clears `global.mongoose` + SQL pools (`:81-90`)
3. `mongoose.connect(effectiveUri)` (`:115-127`) — **NO `assertSafeUri()`** → unguarded SSRF
4. `migrateConnections(oldUri, uri)` (`:159-169`) → `readConnectionsFromSource` then
   `writeConnectionsToTarget` (`migrate/migrator.js:305-328`) — **copies all connection records
   from prod into the attacker DB**

Impacts: process-wide DB hijack (mongoose is a singleton — all users, until restart), data
exfiltration via auto-migration, unguarded SSRF, raw-driver-error oracle (`:129-131`), DoS.
The F-08 loose relay substring regex is copy-pasted here too (`:99`).

**`assertSafeUri()` has exactly ONE call site in the whole codebase** (`test-uri/route.js:93`).
`/api/settings/database` never calls it.

Chain is now shorter and doesn't need F-07:
register (F-06, no verification) + F-05 (cap bypassed) → POST /api/settings/database → prod DB
repointed + records exfiltrated. Unauthenticated → full compromise.

**Only 2 routes under `src/app/api/settings/`**: `database/route.js` and `database/migrate/route.js`
(the latter has the identical session-only pattern at `:15-18`). Narrow blast radius, easy fix.

Rating → **D-**. Would be F if F-10 were confirmed live; holding one grade because it's
source-verified only. R-0 (updated) closes BOTH criticals — same route, and it's a same-day fix.
