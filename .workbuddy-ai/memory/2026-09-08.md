# 2026-09-08

## Fixed: local relay connection detection was one-shot

Symptom: after installing the local relay successfully, the SSH Monitor still showed
"Relay not connected" / "Local relay agent is offline." It only cleared after manually
clicking the retry button in the sidebar banner.

Three independent defects, all in `src/context/AppContext.js`:

1. Effect "5. Fetch relay status once on mount" — literally fetched
   `/api/relay/token` once. `relayInfo` never updated.
2. Effect "6. Health polling — every 20 seconds" — **no `setInterval` anywhere in
   the file** (verified: `grep -n "setInterval\|setTimeout"` → NONE). `relayDown`
   was computed once at mount. The comment lied.
3. `relayDown` came from `/api/health`, whose `relay.up` is
   `global.__activeRelays?.size > 0` — whether ANY tenant has a relay. Wrong
   per-user in both directions.

### Changes

- **New `src/utils/relayStatus.js`** — `fetchRelayStatus()` (user-scoped,
  `cache: 'no-store'`, throws on non-ok), plus a `relay-status-changed` event bus
  (`requestRelayStatusRefresh` / `onRelayStatusRefresh`) so anything that changed
  relay state can force an immediate re-read.
- **`AppContext`** — replaced both one-shot effects with:
  - A continuous relay poller: 5s while missing (backing off to 20s after
    ~2 min via `missingTicks`), 20s when attached, 60s hidden, immediate on
    `visibilitychange` / `focus` / `online` / bus event. Gated on
    `sessionStatus` (endpoint 401s when unauthenticated). Uses
    `fetchConnectionsRef` so the loop isn't torn down on every `dbConfig` change.
  - On relay recovery: pins `ssh_monitor_ssh_mode=local` and
    `ssh_monitor_preferred_relay` **before** refetching (apiFetch reads both from
    localStorage at call time), then refetches only on a real down→up transition
    or an actual change — never on a no-op first reading.
  - A real 20s `setInterval` for `/api/health`, mongo only.
  - `relayDown` is raised only when the browser shows relay intent.
  - No-op dispatches skipped via `relayDownRef` / `mongoDownRef` mirrors, so the
    20s timer doesn't re-render every consumer.
- **`MongoDeadBanner`** — retry now uses `fetchRelayStatus()` instead of the global
  health flag; dismissal re-arms on a later outage; server-mode check reads
  `ssh_monitor_ssh_mode` only (the `preferred_relay` fallback held a relay *name*,
  never a mode).
- **`RelayPairingPanel` / `SettingsApp`** — nudge the poller on pairing approval and
  on install success, so no manual retry is needed.

## Follow-up (same session)

### Pre-existing test failure was a false alarm — fixed
`relayToken.test.mjs` "supporter gate is enforced at the relay WebSocket" failed.
Verified against `server.js`: the gate **is** there (`isRelaySupporter(entry)` at
line 5231, inside the `relayWss.on('connection')` handler). The test's regex
allowed only 1600 chars between the handler and the call; actual distance is 2038
because the code is comment-dense. Widened to 3000, and widened the sibling
`entry.lastUsed` assertion too (1400 → 3000) since it had only 288 chars of
headroom and would have broken the same way on the next comment edit.
`npm test` now **400/400**.

### Broke then fixed the dev server (my fault, worth remembering)
To verify the build I ran `NEXT_DIST_DIR=.next-verify npx next build`. `.gitignore`
had `/.next/`, which does **not** match `.next-verify`, so Tailwind v4's auto source
detection scanned it, pulled mangled arbitrary-value utilities out of its Turbopack
cache, and the dev server 500'd on `Parsing CSS source code failed`.
Fix: removed `.next-verify`, cleared `.next/cache/turbopack`, wildcarded the ignore
rule to `/.next*/`. Dev server then returned 200 with zero CSS errors.

### Runtime verification actually performed
- Dev server boots: `GET /` → 200, no CSS errors.
- `GET /api/relay/token` unauthenticated → 401 `{"error":"Unauthorized"}` — confirms
  both the auth gate and that `fetchRelayStatus()` correctly throws on non-ok (which
  is why the poller is gated on `sessionStatus`).
- `GET /api/health` → `relay.up: false` (global count, 0 relays attached) — the exact
  unreliability that made it unfit as a per-user signal.
- `relay-status-changed` present in a served client chunk, so the new module ships

  by a live browser. A real end-to-end check needs a signed-in session plus an
  actual relay.
