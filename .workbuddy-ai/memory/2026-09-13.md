## ROOT CAUSE — production Hermes "green stuck background" (user: prod green, localhost fine)

**Cause: a poisoned browser-cache entry on the `monitor.eaqdragon.com` origin.**
Found by scanning the user's Chrome caches on disk (`~/Library/Caches/Google/Chrome/*/Cache/Cache_Data`):

```
URL:          https://monitor.eaqdragon.com/api/agents/webui-proxy/m/<conn>/9119/assets/index-DY9avcdQ.js
content-type: text/html; charset=utf-8          <-- HTML where JS is required
cache-control: public, max-age=31536000, immutable
cf-cache-status: MISS      (origin response, not Cloudflare)
date:         2026-09-13 05:41:30 GMT  (= 12:41 Bangkok)
```

`index-DY9avcdQ.js` is Hermes' **entry module**. The browser refuses to execute a
module whose MIME is `text/html` ("Failed to load module script"), so the entry
never runs and Hermes' static boot splash stays forever = the green screen.
`immutable` means it is **never revalidated** — a normal reload cannot fix it;
only a hard reload / "clear site data" / a URL change can.

The same URLs cached under `localhost:3030` are **real JS** — which is exactly
why localhost renders the full dashboard. The poison is per-origin.

### Why it came back now

- `4680c2d7` added `?v=<epoch>` to hashed assets **specifically to escape this
  poisoned URL** — and that is the era the user's 19:55 screenshot falls in.
- `8e4f604d` removed the epoch (correctly: a query suffix splits the module
  graph). But removing it also re-pointed the app at the bare poisoned URL.
  So both eras are green, for two different reasons.

### Why `?v=` splits the module graph (measured against the real bundle)

Fetched Hermes from a local `hermes dashboard --skip-build --port 9119` and read
the emitted bundles:

- dynamic import: ``import(`./ConfigPage-X.js`)`` → resolved by the **browser**
  against the **module URL**; RFC 3986 **drops the base query**.
- preload deps: `__vite__mapDeps` returns `"assets/X.js"`, and the helper emits
  `"/" + dep` → **origin-root-absolute**. (This is why `rewriteRootAssetRefs`
  writes `relPrefix` *without* a leading slash.)

Both agree on `/api/agents/webui-proxy/m/<conn>/<port>/assets/X.js` — until a
`?v=` is added, which the preload keeps and the import loses → two module
instances → `SystemActionsProvider` context split → green splash. A **path**
segment survives both rules, a query string survives only one.

### Tooling gotcha (cost real time, general)

**Do NOT batch several edits to the SAME file in one message.** Eight edits to
`MEMORY.md` all reported "Successfully edited", but only **one** survived — each

## Boot sequence stuck at 80% on production — ROOT-CAUSED AND FIXED

**Reported:** *"on production why stuck at 80% on boot sequence need to click
skip like fail to check database"*.

### The arithmetic pins the gate exactly

`BootSequence.js` computes `totalSteps = BOOT_LINES.length + 4` and
`progressPercent = (staticProgress + dynamicStep) / totalSteps`. `BOOT_LINES`
has **16** entries, so `totalSteps = 20` and **all-16-static-done with
`dynamicStep === 0` is exactly 80%.** No other state lands on 80 — dynamicStep
1/2/3 give 85/90/95%. So "stuck at 80%" means *the dynamic phase never advanced
past its first step*.

`dynamicStep` only leaves 0 when `sessionStatus === 'ok' && serverStatus === 'ok'`.
Since the on-screen text was the database one, `serverStatus === 'error'`.

The relay gate is **not** a stall point: `AppContext.applyStatus()` dispatches
`checkDone: true` *before* it branches on `connected`, so a relay-less browser
still resolves `relayStatus` → step 3→4 always fires.

### Why `/api/health` said 503 while the database was fine

`src/app/api/health/route.js`:

```js
const status = memory.safe && mongoUp ? 'ok' : 'degraded';
... { status: status === 'ok' ? 200 : 503 }
```

**The relay flag is not in that expression** — it is reported, never decisive.
So a 503 whose body says `mongo.up: true` can only mean `memory.safe === false`.
I had one such response from prod earlier today, so this is deduction, not a
guess. (Confirmed prod runs this exact route: the pre-hardening version also
disclosed `mongo.readyState`, `relay.count` and `memory.safe` — see F-01 in
`docs/SRC_ASSESSMENT_2026-09-03.md` — and prod returns none of them.)

### Two independent bugs, both real

1. **`checkMemory()` is wrong on Linux production.** It gates on
   `os.freemem()`, which on Linux is libuv's `sysinfo(2).freeram` = **MemFree —
   page cache and reclaimable slab excluded**. A healthy box that has served any
   I/O reports a few hundred MB "free" while `MemAvailable` is gigabytes, so
   `sysFreeMB > 512` trips on a machine that is nowhere near out of memory.
   **This exact bug class was already found and fixed for darwin on 2026-08-30**
   (`c3724484`: *"os.freemem() excludes purgeable/compressed memory and reports
   near-zero on healthy machines"*) — the Linux branch was left at 512.
   Corroboration on this very Mac: `os.freemem()` = **383 MB** while completely
   healthy. Docker adds nothing here — no `mem_limit` in compose, and
   `/proc/meminfo` inside a container is the *host's*, with Mongo 7's WiredTiger
   cache defaulting to ~50% of RAM.
2. **`BootSequence` was the only consumer that read the status code instead of
   the body.** `AppContext.js:766` (`data.mongo?.up ?? res.ok`) and
   `MongoDeadBanner.js:68` (`!!healthRes.mongo?.up`) both read the flag;
   `BootSequence.js:843` did `dbDown = body.status === 'degraded' || res.status === 503`,
   so *any* degraded 503 — including a pure memory-pressure trip — was reported
   as **"Central database is unreachable"** and halted the boot, forcing Skip
   past a working app.

### Fix

- `src/lib/serverGuard.js` — new `getFreeMemMB()` reads `MemAvailable` from
  `/proc/meminfo` on Linux, falls back to `os.freemem()` elsewhere (incl. when
  `/proc` is absent). 512 MB floor now means what it says.
- `src/utils/healthProbe.js` (new) — `classifyHealth(res, body)` returns
  `{ ok, dbDown, degraded }`. The body is authoritative; `mongoUp === true` ⇒
  ok (degraded if the HTTP status was not 2xx), `mongoUp === false` ⇒ dbDown,
  2xx with an unparseable body ⇒ ok (preserves the old 200 behaviour).
- `src/components/landing/BootSequence.js` — both probes classify through it.
  Degraded-but-reachable now renders a non-blocking `[ WARN ]` line and the
  footer reads `link degraded`; only `dbDown` still halts.
- `tests/bootHealthProbe.test.mjs` (new) — 9 tests, using the **real prod
  payloads**, plus a source-level anti-drift assertion that the boot screen
  still calls the shared classifier (a component that reverted to the
  status-code check would otherwise pass every behavioural test).
