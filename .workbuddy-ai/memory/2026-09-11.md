## "Web Browser app can't access any url — localhost refused to connect"

### Diagnosis (measured, not guessed)
Reproduced with headless Chrome + a locally-minted `next-auth.session-token`
(`encode()` from `next-auth/jwt`; middleware/route handlers call `getToken` and
never touch Mongo, so a signed token is enough to get past the auth gate).

CDP `Network.loadingFailed` gave the real reason:

    url    /api/browser/proxy?url=https%3A%2F%2Fexample.com
    error  net::ERR_BLOCKED_BY_RESPONSE
    reason coep-frame-resource-needs-coep-header   (type=Document)

The frame ended as `chrome-error://chromewebdata/`. Not a proxy bug, not a CSP
`frame-src` bug, not SSRF — the proxy itself returned 200 with correct HTML.

### The rule
Isolated it with a throwaway origin (`scratch/coep-isolate.mjs`), parent always
`COEP: credentialless`:

| child COEP | result |
| --- | --- |
| `unsafe-none` | BLOCKED `coep-frame-resource-needs-coep-header` |
| (absent) | BLOCKED |
| `credentialless` | loads |
| `require-corp` | loads |

So a nested document must declare a COEP at least as strict as its embedder's.
`unsafe-none` is not an opt-out — it is a rejection. **Same-origin does not
exempt it.**

The app shell sends `credentialless` (server.js, next.config, `proxy.js`
CROSS_ORIGIN_HEADERS) while `/api/browser/proxy` and `/api/agents/webui-proxy`
both sent `unsafe-none` → every in-app iframe was unrenderable. The route's
*error* pages also carried `unsafe-none`, so even "Address Blocked by Security
Policy" was replaced by a blank blocked frame — that is why nothing explained
itself.

### Fix
One COEP value, shared:
- `coepValue()` in `server.js` (also accepts `0/false/off` for the documented opt-out)
- `COEP` const in `next.config.mjs`, now used by **both** framing rules
- `credentialless` in both route handlers (browser proxy safeHeaders + error
  page; webui proxy `frameHeaders` + `outHeaders`)
- `.env.example`: the documented escape hatch was `COEP=0`, which the code
  never matched (`=== 'unsafe-none'`). Now documented correctly.

### Verification
- `/` and both proxy routes report `coep: credentialless`.
- Framed `https://example.com` → `title: "Example Domain"`; `https://www.google.com`
  → `title: "Google"`. SSRF-blocked URL now renders the error card in-frame.
- End-to-end through the real desktop app: opened **Web Browser**, typed
  `google.com` into the omnibox → viewport iframe `title: "Google"`, no error.
- `npm test` 463/463. Per-file eslint 0 errors on all touched files.
- Verified on an isolated `NEXT_DIST_DIR=tmp/verify PORT=3031` instance so the
  running dev server on 3030 was never disturbed.

## Follow-up: closed the same-origin hole with a sandboxed frame

The flagged item above ("proxy serves third-party HTML same-origin") is now fixed.

`/api/browser/proxy` pages are rendered in a frame with
`sandbox="allow-scripts allow-forms allow-popups allow-modals"` — no
`allow-same-origin`, so the proxied page gets an **opaque origin** and can no
longer read app cookies, DOM, or storage. Verified: the parent genuinely cannot
reach into the frame (`contentDocument` throws).

Two consequences had to be solved, both empirically:

1. **The page must not navigate itself.** An opaque origin makes the frame's own
   navigations cross-site, so `SameSite=Lax` session cookies are withheld and
   every link click landed on a 401. Fix: the injected bridge posts
   `{ __mpBrowser: 'goto', url }` and the **parent** performs the navigation
   (`navigateTab` assigns `frameSrc`). The parent also owns the per-tab history
   stack, so Back/Forward work again.
2. **The page must not build proxy URLs.** A root-relative `/api/browser/proxy`
   inside the page resolves against the page's own `<base href>` (the *target*
   origin), giving `https://example.com/api/browser/proxy?...` →
   `corp-not-same-origin-after-defaulted-to-same-origin-by-coep`. The parent
   builds every proxy URL; the page only ever reports absolute target URLs.

Also fixed while in there: the omnibox showed the internal proxy wrapper instead
of the real destination; and Reload fell back to the unwrapped `url`, bypassing
the proxy entirely.

Sandboxing is COEP-neutral — Chromium's rule only inspects the response header,
so `credentialless` remains correct on the proxied response.

`webui` tabs are deliberately **not** sandboxed; they need same-origin.

Verification: full suite 466/466; `scratch/browser-app-e2e.mjs` 10/10 for both
`example.com` and `google.com`, and re-run against the **live** dev server on
3030 (the fix is already serving there).

Known cosmetic costs (not fixed, not blocking): cross-origin webfonts are
CORS-blocked from an opaque origin, so proxied pages lose webfonts; and only
navigation is rewritten, not fetch/XHR, so proxied SPAs still throw CORS errors.

## Unrelated flake found and fixed: `tests/relay-agent-pair.test.mjs`

`npm test` failed once on *"dependency install is split and bounded"* — a test
that has nothing to do with the browser work. Cause: `runAgent()` mints its temp

line that contains a randomly-generated path.**

## Measured what the sandboxed frame can actually do — and reversed a claim

I had written (in this log, and in MEMORY.md) that "proxied SPAs throw CORS
errors". That was **inferred from the design, not measured**, and measurement
mostly contradicts it. Two new harnesses:

- `scratch/browser-fidelity-probe.mjs` — loads a site in the real app and reports
  rendering + subresource failures.
- `scratch/browser-xhr-probe.mjs` — runs the experiment *inside* the frame.

**Instrument bug worth remembering**: CDP `Network.loadingFailed` does **not**
fire when a response is merely withheld by CORS — the network request succeeds
(200) and only the READ is denied. A probe counting only `loadingFailed` reports
"0 failures" on a page whose every font and XHR was CORS-blocked. I initially hit
exactly that false negative. The fidelity probe now also counts `Log.entryAdded`
entries matching `blocked by CORS`.

### Rendering (fidelity probe)

| site | result |
| --- | --- |
| example.com | renders, 0 failures |
| en.wikipedia.org | renders, 9005 chars of text, 8 stylesheets, 23 images, 0 failures |
| news.ycombinator.com | renders, 0 failures |
| iana.org | renders; **1 webfont lost** (`net::ERR_FAILED` + CORS from `origin 'null'`); 1 ad-tech iframe blocked by our own COEP rule |

### Runtime capability (xhr probe, run inside the frame)

    [BLOCKED] fetch same-target-relative (/robots.txt)         TypeError: Failed to fetch
    [ok     ] fetch cross-origin, ACAO:* (api.github.com/zen)  status 200
    [BLOCKED] fetch cross-origin, no CORS                      TypeError: Failed to fetch
    [BLOCKED] XHR same-target-relative                         Error: network error
    [BLOCKED] document.cookie                                  SecurityError
    [BLOCKED] localStorage / indexedDB.open / serviceWorker     SecurityError
    [ok     ] location.origin                                  http://localhost:3030   <-- see below
    [ok     ] document.baseURI                                 https://example.com/

Two things fall out of this:

1. **`location.origin` LIES in a sandboxed frame.** It reports the URL's origin
   (`http://localhost:3030`) rather than `null`. The real origin *is* `null` —
   proven by the `SecurityError`s on storage APIs and by the `from origin 'null'`
   in the CORS error text. Do not use `location.origin` to detect opacity; use
   `document.cookie` or the CORS message.
2. **Assets never go through the proxy at all** — `<base href>` points at the
   target, so CSS/images/fonts load *direct* from the target site and need no
   CORS. Only navigations consume the 60 req/min limiter.

### Decision: do NOT route fetch/XHR through the proxy

The accurate statement is narrower than what I originally wrote: a page's own
*same-site relative* `fetch`/XHR fails; cross-origin calls to `ACAO: *`
endpoints work fine. Making relative calls work would mean rewriting
`fetch`/XHR in the injected script and returning `ACAO: null`/`*` from the proxy.
Rejected because:

1. **Cookie/Authorization are stripped on purpose** (`route.js` outbound
   headers). Authenticated APIs can therefore never work — the frame would
   render a logged-out shell. That is the common case for any SPA worth having
   an in-app browser for.
2. **The 60 req/min/IP limiter only counts navigations today.** An SPA would
   exhaust it in seconds, so the anti-automation guard would have to be raised
   or dropped.
3. **It requires relaxing our own CORS** — the opaque frame can only read a
   response carrying `ACAO: null`/`*`, turning the proxy into a CORS-readable
   relay. Trading a real hardening for a cosmetic gain, one day after closing
   the same-origin hole.
4. **Measured value is low**: the reading use cases already work (table above).

If this is ever revisited, those three constraints have to be re-decided first —
not worked around silently.

## Fixed: `target="_blank"` opened a logged-out OS popup

While checking whether the sandbox had broken anything I had not tested, I found
`target="_blank"` was untested. The injected click interceptor deliberately
skipped it:

    if (a.target === '_blank') return;

so the anchor fell through to the browser's native popup — which **inherits the
frame's opaque origin**. Measured (`scratch/browser-blank-link-probe.mjs`): the
popup rendered the target site with `document.cookie` → `SecurityError`, i.e.
logged out, in a separate OS window outside the app's own tab bar.

That is wrong for an app that already has tabs, and it is not what any real
browser does — Chrome/Safari/Firefox open `_blank` in a new **tab**.

Fix:
- `route.js`: the interceptor no longer bails on `_blank`; `goto(u, kind)` takes
  a kind and posts `{__mpBrowser:'newtab', url}`. Normal clicks still send `'goto'`.
- `AgentWebUIBrowserApp.js`: `openWebTab(url)` creates a proxied web tab via
  `handleNewTab`, which is now a `useCallback` (stable identity, so the bridge
  effect stops re-subscribing every render) and seeds `history`/`historyIndex`
  from birth — otherwise Back has nothing to pop.
- The bridge effect handles `'newtab'` alongside `'goto'`/`'nav'`.

### Instrument note

Frame count is **not** a valid signal here: the app only mounts the ACTIVE tab's
iframe, so "a new tab opened" and "the same tab navigated" both leave exactly one
proxy frame in the DOM. My first probe therefore reported a false failure. The
tab bar is the only thing that distinguishes them — count the children of the
"Open New Tab" button's parent, minus the button.

### Verification

`scratch/browser-blank-link-probe.mjs` → **7/7**: 1 → 2 tabs, no OS popup
escaped, the new tab became active, and the omnibox shows the real destination
rather than the proxy wrapper. Regression-checked normal navigation with
`browser-app-e2e.mjs` → still **10/10** (in-place link click + Back unaffected).
Full suite **467/467**; per-file eslint clean.

## Fixed: `history.pushState` threw, killing SPA routers

Extending the capability probe with the other boot-time APIs a page uses found a
second real defect:

    [ok     ] history.replaceState(same URL)              ok
    [BLOCKED] history.pushState(/deep/link)               SecurityError
    [BLOCKED] history.pushState(absolute, other origin)   SecurityError

**An opaque origin cannot change its own URL.** `replaceState` to the *same* URL
is allowed; any `pushState` to a different path throws. That throw happens
**inside the page's own click handler**, so a React Router / Vue Router app dies
on the first client-side navigation and the site stops responding.

The agent WebUI tunnel solves the same problem by *containing* the URL
(`ASSET_PREFIX + pathname + query + hash`) — that trick does **not** transfer,
because that frame is same-origin while ours is opaque, so even a same-origin URL
is refused. So the injected script **swallows** `pushState`/`replaceState`
(never delegating to the original, which throws) and posts
`{__mpBrowser:'push', href}`. The page keeps its own state and renders its own
view; the omnibox follows the route like a real browser would.

### The follow-on bug, and why it matters

The parent's `applyFrameUrl` looked like a generic "set the URL" helper. It is
not: it *unwraps* a `/api/browser/proxy?url=…` wrapper and returns early for
anything else. Feeding it a bare destination silently did nothing — the omnibox
stayed put and the first e2e run reported the failure. Added `applyPushedRoute`,
which takes the real target URL directly, matching the rule that the parent
builds proxy URLs and the page never does.

Worth remembering: two messages that both "update the current tab's URL" needed
two different handlers because they carry differently-shaped payloads.

### The backtick trap, personally

The explanatory comment I wrote for the pushState handler used backticks around
`history.pushState({}, '', '/route')`. **Those backticks terminated the
template literal**, leaving the rest of the injected script as top-level garbage
— a guaranteed 500 on the route. Per-file eslint caught it as
`Parsing error: Missing semicolon`. This is the exact trap already recorded in
MEMORY.md for the WebUI proxy, and I walked straight into it.

Added a test that captures the literal body and asserts it runs to the end of
the script, so `npm test` catches it rather than relying on someone remembering
to lint that one file.

### Verification

`history.pushState` → **ok** in-frame (was SecurityError). `browser-app-e2e.mjs`
extended with two checks → **12/12**, including "SPA route change reaches the
omnibox". Full suite **469/469**; per-file eslint clean; route serves 401
(unauth, not 500).

### Also

Saved the reusable method as a skill: `~/.workbuddy-ai/skills/embedded-frame-diagnose/`
— minting a session, CDP `blockedReason`, the two-instrument rule
(`loadingFailed` vs `Log.entryAdded` for CORS-withheld), running the experiment

## Fixed: a POST form killed the whole tab

The last untested interaction the sandbox had changed. `route.js` had a
one-line bail-out:

    if (m === 'post') return;

so a POST fell through to the browser's default behaviour: the sandboxed frame
navigated **itself** straight to the target origin. Only the proxy emits the
COEP header a nested document needs, so the frame died:

    [Document] net::ERR_BLOCKED_BY_RESPONSE
               (corp-not-same-origin-after-defaulted-to-same-origin-by-coep)
               https://example.com/probe-post

— the same `chrome-error://chromewebdata/` blank tab as the original COEP bug,
except this time the trigger was a form, not a link. (The failure mode is
familiar: `corp-not-same-origin-after-defaulted-to-same-origin-by-coep` is the
signature of *anything* that navigates the sandboxed frame to a foreign origin.)

### Fix

- **GET** is proxied properly: build the query from `URLSearchParams(form.action)`
  plus `new FormData(form)` entries, then hand the absolute URL to `goto`.
- **Non-GET** is `preventDefault()`ed and explained in-page rather than silently
  swallowed — a POST cannot work in an opaque-origin frame, so the honest thing
  is to say so. `explainBlockedSubmit()` injects a transient card
  (`#__mpBlockedNotice`, 12 s auto-dismiss) pointing at the toolbar's
  open-externally button. It deliberately contains **no** external-open link: a
  proxied page must never be able to trigger a browser-tab open.
- `method="dialog"` is left alone — it closes a `<dialog>` and never navigates.
- `HTMLFormElement.prototype.submit` is patched to route through the same
  handler, because `form.submit()` **fires no `submit` event** and would
  otherwise bypass the interceptor entirely.

### Two instrument bugs on the way there

1. **`form.submit()` is invisible.** My first probe used it and reported that
   even the GET control "escaped" — because the submit event never fired, so the
   interceptor was never consulted. Switched the user-path probe to
   `requestSubmit()`, which does fire the event; kept `submit()` as a separate
   check that the prototype patch holds.
2. **Counting one instrument again.** Same lesson as the CORS-withheld case: the
   `blockedReason` only appeared on `Network.loadingFailed` for the *document*,
   not for the form POST itself — the POST is a navigation, so it shows up as a
   document load, not a subresource.

### Verification

`scratch/browser-post-form-probe.mjs` → **6/6** (GET navigates and the omnibox
follows; POST is refused, notice appears, no chrome-error, frame survives).
Full suite **470/470**; `browser-app-e2e.mjs` **12/12**; per-file eslint clean;
route serves 401 unauth, not 500.

## Found the actual MEMORY.md size limit: 8000 chars

Every previous consolidation was guesswork about how much to cut. I found the
real rule by grepping the app bundle:

    /Applications/WorkBuddy AI.app/Contents/Resources/app.asar
      → MemoryCollector.getWorkingMemoryContent()
      → var MAX_MEMORY_CHARS = 8e3;

So the cap is **8000 characters of JS string length** (`content.length`, after
`.trim()`), not bytes. User-level `~/.workbuddy-ai/MEMORY.md` has its own,
separate cap of 4000 chars (`MAX_USER_MEMORY_CHARS`), also measured on
`.length`. Over either, the content is silently `substring(0, cap)`-ed and the
"ACTION REQUIRED" banner is appended.

Useful gotcha for measuring: the file contains `→`, `±` and `—`, so `wc -c`

    grep -abo "MEMORY.md is too large" app.asar     # → byte offset
    dd if=app.asar bs=1 skip=<offset-2000> count=5000 | tr -d '\000'

## Closed the last documented TODO: `webui:fail`

MEMORY.md had carried this open item for a while:

> Open: add `webui:fail` so `handleWebuiForward` errors don't cost the full
> 20 s ack timeout (needs relay rebuild).

I went to verify it was still real before "fixing" it, and it was — but it was
worse than the note said. The note described a latency bug. The actual defect
was a **misdiagnosis**.

### What was actually wrong

The relay's dispatch was:

    case 'webui:forward': handleWebuiForward(msg).catch(err => console.error(`✗ [Relay WebUI] ${err.message}`)); break;

So when the tunnel failed — SSH auth refused, the agent's Web UI port dead, the
port range exhausted — the relay logged locally and sent **nothing**. The
server's waiter (`__waitForWebuiForward`) therefore could not tell the two
situations apart and sat out its full 20 s, then answered:

    Local Relay did not confirm the Web UI tunnel. Check that Local Relay is
    running on your computer and can reach this server over SSH.

That advice is *wrong* when the relay is connected and healthy. The user is
told to check something that is fine, and the real reason (which the relay
knew and printed on the user's own machine) never reaches the tab. Same class
of bug as the original "Opening Web UI…" hang: a failure that cannot explain
itself.

### The fix

Two failure channels, kept distinguishable end to end:

| channel | meaning | HTTP |
| --- | --- | --- |
| `webui:ready` → `{ port }` | tunnel is up, verified | 200 |
| `webui:fail` → `{ error }` | **relay is up**, tunnel failed | **502** |
| (timeout) → `{ timedOut: true }` | no relay / relay too old | 504 |

- `public/local-relay.js`: new `reportWebuiFailure(msg, err)` replaces the bare
  `console.error`. Still logs locally (that log is the only place with full
  detail), then sends `{ type: 'webui:fail', forwardId, error }` when the socket
  is open. Best-effort — a throw in the reporter must never mask the original
  error, so the server's timeout still covers it.
- `server.js`: the waiter now resolves `{ port, error, timedOut }` instead of a
  bare port, and a new `webui:fail` branch resolves it immediately with the
  reason (length-capped at 300 chars — it is relay-supplied input).
- `nanobot` + `hermes` routes: `ack?.error` → **502** quoting the relay's own
  message; no error → the existing **504** timeout text, unchanged. An old relay
  that never answers still lands on the 504 path, so this is backward-compatible.
- No client change needed: `AIAgentsApp` already writes `rr.error` verbatim into
  the fail card and the notice.

502 vs 504 is the semantic distinction that was missing: "an upstream service I
depended on failed" versus "nothing answered in time".

### Verification

- **The relay function is executed, not grepped.** `tests/webui-forward-ack.test.mjs`
  lifts `reportWebuiFailure` out of the shipped source with `new Function` and
  runs it against a stub socket: asserts the exact `webui:fail` payload, that a
  missing `forwardId` sends nothing, and that a dead/throwing socket does not
  throw. Source-regex assertions alone would have passed on a typo.
- Relay artifact rebuilt deterministically; `build-relay.mjs --check` clean
  (source `11b7f2eb99b4…`). The server serves only the artifact, so this matters.
- Route smoke test on an isolated `PORT=3031` instance: both routes answer
  **401** (auth), not 500 — the edits parse and the modules load.
- Full suite **489/489** (was 470; +19). Per-file eslint 0 errors.

### Deployment consequence — the two halves ship separately

The **sender** of `webui:fail` is the relay, which runs on the user's own
machine as an obfuscated install at `~/.ssh-monitor-relay/`. The server half
(the 502 handling) is live the moment this deploys, but an **un-updated relay
behaves exactly as before** — it never answers, so the route still takes the 504
timeout path. That is the backward compatibility working as designed, not a bug.

To actually get the better error on a given machine, the relay there must be
reinstalled/re-paired (`local-relay --pair`; there is no self-update). Worth
remembering before concluding the fix "didn't work" on a box with an old relay.

Also confirmed while checking: `public/local-relay.min.js` is gitignored
(`.gitignore:62`), so it is build output, not a tracked file — `predev`/
`prebuild` regenerate it. `server.js:547` serves the artifact and the readable
source is only a reference, so editing `public/local-relay.js` alone changes
nothing that ships until the artifact is rebuilt.

### Two tests I had to fix, and one I had to delete

- `tests/ai-agents-webui-open.test.mjs` asserted `Number(ackedPort) || 0` — the
  old bare-port contract. Its *intent* ("relay-start fails instead of handing
  the browser a guessed port") is still right, so I updated the mechanics to
  `Number(ack?.port) || 0` and kept the anti-guess guard.
- In my own new file, an assertion expected `error: error` while the code used
  the shorthand `error,`. The code was right; I made the assertion accept both.
- I **deleted** a test I had written that asserted the nanobot and hermes
  relay-start branches are byte-identical apart from one noun. It failed, and it
  deserved to: they legitimately differ (nanobot forwards a bootstrap secret,
  hermes does not; different requested ports). Replaced with an assertion that
  the *failure handling* matches in both — which is what I actually cared about.

That last one is the useful lesson: an equality assertion between two things
that are merely similar is a test that will fight you. Assert the property you
want, not the shape you happened to observe.

### `server.js` needed partial staging

It is the only file touched by two of the four commits: the COEP hunks sit at
lines 43–601, the ack hunks at 716 and 5487. Staged the COEP half with
`git apply --cached` on a hand-split patch (`scratch/split-server-patch.mjs`),
then committed the remainder cleanly, since after the first commit the working
diff for that file *is* the ack change.

Two things that bit me in that script, both worth remembering:

- **A split patch must end with a newline.** Splitting `git diff` output on
  `\n` puts the trailing empty element only in the last group, so the first
  group's file had no final newline and `git apply` said `corrupt patch at
  line 68` — an off-by-one that looks like a content problem and is not.
- **Do not build a script with a heredoc in this shell.** `cat > f <<'EOF'`
  still expanded `${...}` and died with `Bad substitution: coep.map`. Write the
  file with the editor tool instead.

### Browser chain fix: explain limits instead of faking a browser

The in-app browser cannot safely grant `allow-same-origin`: third-party HTML is
served from the monitor origin, so that would let target JavaScript run as the
app. In the opaque sandbox, storage APIs throw and target scripts/fetches need
CORS from origin `null`. A measured in-memory storage shim got YouTube to a 997
KB DOM but still zero visible text, and made Google self-navigate into a dead
end; it was removed.

`src/app/api/browser/proxy/route.js` now shows a persistent top-level notice for
JS-heavy pages that render an empty shell, and a specific notice for Google's
JS-only search fallback recommending DuckDuckGo Lite. It also keeps
programmatic same-frame `window.open` navigations inside the parent bridge,
refuses page-triggered popups, and returns an explanatory iframe page instead
of bare `Unauthorized` when an opaque frame self-navigates and loses its
session cookie. `tests/browser-proxy.test.mjs` pins these contracts.

Measured end-to-end: YouTube notice, Google notice, Wikipedia clean, Bing clean
(**4/4**). Full suite **491/491**; targeted proxy tests **16/16**; touched-file
ESLint clean. The remaining limitation is intentional: arbitrary JS-heavy
sites still need the external-browser button; the app now says why instead of
looking dead.
