# 2026-09-09

## Mobile/responsive audit across all 15 apps (320 / 375 / 414px)

Built a headless-Chrome geometry harness in `tmp/mb-harness/` (throwaway, not
production): `mint.mjs` (next-auth session), `harness.mjs` (onboarding seed +
overlay hiding + TouchEvent icon tap), `probe.mjs` (per-app measurement),
`summarise.mjs` (report), `svgdiag.mjs` (SVG clipping dump). 45-point baseline
in `probe-baseline.json` / `baseline-report.txt`; after in `probe-after.json`.

Harness gotchas worth keeping:
- `DesktopIcon` needs real `TouchEvent`s on mobile — `dblclick` does nothing.
- Pages in one browser share localStorage; use `browser.createBrowserContext()`
  per measurement or app N's window leaks into app N+1.
- Separate deliberate `overflow-x-auto` scrollers from genuine overflow
  (`hasScrollerAncestor`) or every data table reads as a false alarm.
- `position: fixed` layers (sidebar backdrop) and decorative glow orbs always
  report as "clipped" against the app window — known false positives.

### Root causes found and fixed
1. **globals.css specificity bug (biggest win).** `.window-container
   [class*="flex"] { min-height: 0 }` is (0,2,0) and beat `button { min-height:
   44px }` (0,0,1). Almost every button class contains "flex", so *every* pill
   and toolbar button rendered 25px tall on a phone. Added
   `:not(button):not(a):not(input):not(select):not(textarea):not([role="button"])`.
2. **Icons collapsing to 0px wide.** Lucide SVGs are flex items; crowded rows
   squeezed them to 0x14 and the icon vanished. Added
   `.window-container svg { flex-shrink: 0 }` (768px block). Killed all the
   "clipped path by svg" findings in server-monitor / activity / auto-deploy /
   firewall with zero new overflow.
3. **Tap-target width.** Only `min-height` was set; added `min-width: 44px`
   for `button, [role="button"]` (not bare `a`).
4. **Docker toolbar.** Right-hand action group needs 328px; with `shrink-0` the
   `flex-1` left group resolved to 0 and `.toolbar-tabs` measured **4px**.
   Stacked the toolbar to two rows under `sm:` → tabs now 194px and scroll.
5. **Fixed-width sidebars starving content.** Mongo Sync `w-56` (224px) left
   96px; Server Backup `w-52` (208px) left ~112px. Both now
   `flex-col sm:flex-row` with a capped, scrollable rail on phones.
6. **Fixed 5-column grids** → `grid-cols-2 sm:grid-cols-3 lg:grid-cols-5` in
   ServerBackup, Rclone, MongoBackup; VirusScanner `grid-cols-4` →
   `grid-cols-2 sm:grid-cols-4`.
7. **Dashboard connections table** `min-w-[400px]` in a 238px card (+162px
   overflow) → `min-w-0 sm:min-w-[400px]`, narrower mobile grid cols, Uptime
   column `hidden sm:*`.
8. **Firewall quick-action row** 791px non-wrapping → `flex-wrap`.
9. **Server Monitor tab strip** ~430px in 288px → `overflow-x-auto` +
   `shrink-0` on tabs.
10. **VirusScanner hover tooltips** (`w-72`, `opacity-0`) still contributed
    170px of scrollWidth → `hidden sm:block` (unreachable on touch anyway).

11. **Tap-target width, round 2.** After (1), buttons were 44 tall but 20-40
    wide. Two more cascade traps: the `:where()` resize reset at globals.css
    ~2264 (`.window-container :where([class*='flex'],[class*='grid']) > *`)
    is **(0,1,0) and NOT inside a media query**, so it beat `button { min-width:
    44px }`. Fixed by re-asserting at (0,1,1) *inside* the mobile block rather
    than editing the reset — editing it would have changed desktop. Also
    `input:not([type])` was missing from the mobile input rule, so Activity's
    typeless search box stayed 38px.

### AI Agents: agent data never routed through Local Relay (fixed)
Symptom: on mobile the AI Agents overview wouldn't load; MacBook fine.
Root cause: `AIAgentsApp` was the ONLY app taking `apiFetch` as a **prop**, but
`OSContext.js:477` mounts every app as `<Component windowId={...} {...w.props}/>`
— no props — so `apiFetch || fetch` silently used bare `fetch()` and dropped
`x-ssh-mode` / `x-preferred-relay`. Measured: headers absent even with
localStorage set to local mode. `getSshConfig` does `conn.sshMode ||
options.sshMode` and the Connection model has NO `sshMode` field, so agent
commands only ever used the relay when host was literally 127.0.0.1.
Fix: pull `apiFetch` from `useApp()` (`apiFetch || ctxApiFetch || fetch`).
Re-measured: `x-ssh-mode: local`, `x-preferred-relay: mbp` now sent.
Other apps are fine — ServerFilesList and ServerCompatPanel take apiFetch as a
prop but their parents DO pass it.
Two follow-on fixes in the same area:
- The "Using a cloud server or phone? Continue with direct connection" bypass
  only called `setForceBypassRelay(true)` (React state). It never wrote
  `ssh_monitor_ssh_mode='server'`, so apiFetch kept injecting `x-ssh-mode:
  local` and every request still went through the relay the user just
  bypassed — a dead button in its own use case, and it reset on every open.
  Now `bypassRelay()` persists 'server' + fires `ssh-mode-changed`.
- AppContext force-pins mode back to 'local' whenever it sees a relay
  (AppContext.js:637), which undid that bypass within seconds. Added a
  `ssh_monitor_relay_optout` guard. Pairing a relay on the device clears the
  opt-out so the user is never trapped on direct mode.
Tests 405/405, eslint 0 errors, build exit 0.
Locked in by `tests/ai-agents-relay-routing.test.mjs` (source-inspection
tests are the convention here). Verified non-vacuous: a mutation check
(`tmp/mb-harness/mutcheck.mjs`) reverts each fix in-memory and confirms all
5 assertions fail — do this for any new source-level test.

Still open: the mobile hard gate at AIAgentsApp.js:1631 blocks the whole app
behind `relayInfo?.connected || forceBypassRelay`; `forceBypassRelay` reads
localStorage which is empty on a fresh phone. If the phone's session doesn't
see the relay as connected it renders "Local Relay Required" and fetches
nothing. User couldn't confirm which screen the phone showed.
Also: Web UI "Open in New Tab" navigates to `http://127.0.0.1:<port>`
(AIAgentsApp.js:814) — only valid in a browser on the relay host, so it can
never work on a phone. Not fixed (the central-proxy fallback was deliberately
removed as buggy).

### Unreadable text (8px/9px) — fixed
Font size was never tracked in the first pass. Found an 8px "PRO" badge in
Settings and five 9px *prose* descriptions in Server Backup, plus 9px badges
elsewhere. One mobile-only rule bumps Tailwind's 6/7/8/9/9.5px arbitrary
sizes to 11px (escaped brackets in the selector; unlayered globals beat
Tailwind's `utilities` layer). Sub-10px went 39 -> 0. **10px left alone on
purpose** — ~213 dense-dashboard labels; enlarging risks re-introducing
toolbar overflow. Re-probed 320/375/414 after: overflow 3->3, tap 3->3,
clipped 30->30, no new overflow. Tests 400/400, build exit 0.

### Tablet band 640/768/1024 re-checked (no regression)
The fix added `sm:`/`lg:` variants, so 640-1024 was the one changed-but-
unmeasured band. 640px (touch mode): 16/16 valid, 0 overflow, 0 sub-44px.
768/1024: every app shows the same 4 overflowing elements — window container,
title bar, title row, content pane — at `left:100, width=viewport-20`, right
edge ~80-100px off-screen. **Pre-existing**, not this change: at 1024 all
`sm:`/`lg:` resolve to original values and the `max-width:768px` block is
inert, yet the finding is identical. It is window default geometry in desktop
mode; fixing it would change desktop sizing (out of scope).
Note: 640 and 768 need different probe modes — below 768 the JS `isMobile`
flag is true and `DesktopIcon` only listens to touch, so `PROBE_MOBILE=0`
(dblclick) yields 0 opened windows. At exactly 768 CSS mobile is active but
JS isMobile is false.

### Gotcha: Tailwind v4 scans .gitignore
Writing a literal example of a mangled utility (e.g. as documentation) into
`.gitignore` or a memory note makes Tailwind re-extract it as a real class and
500 every route with `Parsing CSS source code failed`. Both files now carry a
warning comment instead of the literal token.

### AI Agents: "works on MacBook, can't fetch data on mobile" — ROOT CAUSE FOUND (4th defect)

Reproduced end-to-end in the browser harness (`tmp/mb-harness/phone-sim.mjs`),
not just reasoned about. Two runs, same connection, same request, **only the
`x-ssh-mode` header differed**:
- `x-ssh-mode: server` -> `200 {"success":true,"installed":true,"version":"OpenAI SDK: 2.24.0",...}`
- `x-ssh-mode: local`  -> `500 {"success":false,"error":"Local Relay Agent is not connected..."}`

Chain: `ssh_monitor_ssh_mode` is pinned per **ACCOUNT**, not per device
(AppContext:643 writes `local` for ANY browser that sees the user's relay). A
phone can never run a relay but still sends `x-ssh-mode: local`. Then
`resolveSshConfig` (`src/app/api/server-backup/_ssh.js:20`) treats
`sshMode === 'local'` as a HARD requirement and throws when no relay socket is
live — even for public-IP targets the server can reach directly.

**Fix:** a relay is only strictly required to reach the user's OWN machine.
When no relay is found AND the host is not localhost, return the config
unchanged (direct connect) + `logger.warn`. Localhost still throws — falling
back there would make the server dial its own loopback (SSRF).

Measured after fix: `200`, `x-ssh-mode: local` still sent, no error text.
Mutation-tested both ways (remove fallback -> 2 fail; make it unconditional
-> SSRF test fails). 408/408 tests, 0 eslint errors, build OK.

### Harness gotchas found while verifying (next time, read first)
- `useSupporter` gates on `data.success` — a stub of `{isSupporter:true}`
  without `success:true` silently resolves to NOT a supporter, so the app
  never gets past the supporter screen and you conclude "the probe is broken".
- Detecting the relay gate by `/Local Relay Required/i` is ambiguous: the
  per-agent-card Web UI badge renders the same string in the NORMAL UI. Match
  the full gate heading (`/Local Relay Required Fast Agent Telemetry/`) or
  check for catalog text instead. This produced a bogus "still gated: true".
