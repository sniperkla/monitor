## Mobile/responsive audit across all 15 apps (320 / 375 / 414px)

Built a headless-Chrome geometry harness in `tmp/mb-harness/` (throwaway, not
production): `mint.mjs` (next-auth session), `harness.mjs` (onboarding seed +

Harness gotchas worth keeping:
- `DesktopIcon` needs real `TouchEvent`s on mobile — `dblclick` does nothing.
- Pages in one browser share localStorage; use `browser.createBrowserContext()`
  per measurement or app N's window leaks into app N+1.
- Separate deliberate `overflow-x-auto` scrollers from genuine overflow

- `position: fixed` layers (sidebar backdrop) and decorative glow orbs always
  report as "clipped" against the app window — known false positives.

### Root causes found and fixed
1. **globals.css specificity bug (biggest win).** `.window-container
   [class*="flex"] { min-height: 0 }` is (0,2,0) and beat `button { min-height:
   44px }` (0,0,1). Almost every button class contains "flex", so *every* pill
   and toolbar button rendered 25px tall on a phone. Added
   `:not(button):not(a):not(input):not(select):not(textarea):not([role="button"])`.
2. **Icons collapsing to 0px wide.** Lucide SVGs are flex items; crowded rows
   squeezed them to 0x14 and the icon vanished. Added
   `.window-container svg { flex-shrink: 0 }` (768px block). Killed all the
   "clipped path by svg" findings in server-monitor / activity / auto-deploy /
   firewall with zero new overflow.
3. **Tap-target width.** Only `min-height` was set; added `min-width: 44px`
   for `button, [role="button"]` (not bare `a`).
4. **Docker toolbar.** Right-hand action group needs 328px; with `shrink-0` the
   `flex-1` left group resolved to 0 and `.toolbar-tabs` measured **4px**.
   Stacked the toolbar to two rows under `sm:` → tabs now 194px and scroll.
5. **Fixed-width sidebars starving content.** Mongo Sync `w-56` (224px) left
   96px; Server Backup `w-52` (208px) left ~112px. Both now
   `flex-col sm:flex-row` with a capped, scrollable rail on phones.
6. **Fixed 5-column grids** → `grid-cols-2 sm:grid-cols-3 lg:grid-cols-5` in
   ServerBackup, Rclone, MongoBackup; VirusScanner `grid-cols-4` →
   `grid-cols-2 sm:grid-cols-4`.
7. **Dashboard connections table** `min-w-[400px]` in a 238px card (+162px
   overflow) → `min-w-0 sm:min-w-[400px]`, narrower mobile grid cols, Uptime
   column `hidden sm:*`.
8. **Firewall quick-action row** 791px non-wrapping → `flex-wrap`.
9. **Server Monitor tab strip** ~430px in 288px → `overflow-x-auto` +
   `shrink-0` on tabs.
10. **VirusScanner hover tooltips** (`w-72`, `opacity-0`) still contributed
    170px of scrollWidth → `hidden sm:block` (unreachable on touch anyway).

11. **Tap-target width, round 2.** After (1), buttons were 44 tall but 20-40
    wide. Two more cascade traps: the `:where()` resize reset at globals.css
    ~2264 (`.window-container :where([class*='flex'],[class*='grid']) > *`)
    is **(0,1,0) and NOT inside a media query**, so it beat `button { min-width:
    44px }`. Fixed by re-asserting at (0,1,1) *inside* the mobile block rather
    than editing the reset — editing it would have changed desktop. Also
    `input:not([type])` was missing from the mobile input rule, so Activity's
    typeless search box stayed 38px.

### AI Agents: agent data never routed through Local Relay (fixed)
Symptom: on mobile the AI Agents overview wouldn't load; MacBook fine.
Root cause: `AIAgentsApp` was the ONLY app taking `apiFetch` as a **prop**, but
`OSContext.js:477` mounts every app as `<Component windowId={...} {...w.props}/>`
— no props — so `apiFetch || fetch` silently used bare `fetch()` and dropped
`x-ssh-mode` / `x-preferred-relay`. Measured: headers absent even with
localStorage set to local mode. `getSshConfig` does `conn.sshMode ||
options.sshMode` and the Connection model has NO `sshMode` field, so agent
commands only ever used the relay when host was literally 127.0.0.1.
Fix: pull `apiFetch` from `useApp()` (`apiFetch || ctxApiFetch || fetch`).
Re-measured: `x-ssh-mode: local`, `x-preferred-relay: mbp` now sent.
Other apps are fine — ServerFilesList and ServerCompatPanel take apiFetch as a
prop but their parents DO pass it.
Two follow-on fixes in the same area:
- The "Using a cloud server or phone? Continue with direct connection" bypass
  only called `setForceBypassRelay(true)` (React state). It never wrote
  `ssh_monitor_ssh_mode='server'`, so apiFetch kept injecting `x-ssh-mode:
  local` and every request still went through the relay the user just
  bypassed — a dead button in its own use case, and it reset on every open.
  Now `bypassRelay()` persists 'server' + fires `ssh-mode-changed`.
- AppContext force-pins mode back to 'local' whenever it sees a relay
  (AppContext.js:637), which undid that bypass within seconds. Added a
  `ssh_monitor_relay_optout` guard. Pairing a relay on the device clears the
  opt-out so the user is never trapped on direct mode.
Tests 405/405, eslint 0 errors, build exit 0.
Locked in by `tests/ai-agents-relay-routing.test.mjs` (source-inspection
tests are the convention here). Verified non-vacuous: a mutation check
(`tmp/mb-harness/mutcheck.mjs`) reverts each fix in-memory and confirms all
5 assertions fail — do this for any new source-level test.

Still open: the mobile hard gate at AIAgentsApp.js:1631 blocks the whole app
behind `relayInfo?.connected || forceBypassRelay`; `forceBypassRelay` reads
localStorage which is empty on a fresh phone. If the phone's session doesn't
see the relay as connected it renders "Local Relay Required" and fetches
nothing. User couldn't confirm which screen the phone showed.
Also: Web UI "Open in New Tab" navigates to `http://127.0.0.1:<port>`
(AIAgentsApp.js:814) — only valid in a browser on the relay host, so it can
never work on a phone. Not fixed (the central-proxy fallback was deliberately
removed as buggy).

### AI Agents: "works on MacBook, can't fetch data on mobile" — ROOT CAUSE FOUND (4th defect)

Reproduced end-to-end in the browser harness (`tmp/mb-harness/phone-sim.mjs`),
not just reasoned about. Two runs, same connection, same request, **only the
`x-ssh-mode` header differed**:
- `x-ssh-mode: server` -> `200 {"success":true,"installed":true,"version":"OpenAI SDK: 2.24.0",...}`
- `x-ssh-mode: local`  -> `500 {"success":false,"error":"Local Relay Agent is not connected..."}`

Chain: `ssh_monitor_ssh_mode` is pinned per **ACCOUNT**, not per device
(AppContext:643 writes `local` for ANY browser that sees the user's relay). A
phone can never run a relay but still sends `x-ssh-mode: local`. Then
`resolveSshConfig` (`src/app/api/server-backup/_ssh.js:20`) treats
`sshMode === 'local'` as a HARD requirement and throws when no relay socket is
live — even for public-IP targets the server can reach directly.

**Fix:** a relay is only strictly required to reach the user's OWN machine.
When no relay is found AND the host is not localhost, return the config
unchanged (direct connect) + `logger.warn`. Localhost still throws — falling
back there would make the server dial its own loopback (SSRF).

Measured after fix: `200`, `x-ssh-mode: local` still sent, no error text.
Mutation-tested both ways (remove fallback -> 2 fail; make it unconditional
-> SSRF test fails). 408/408 tests, 0 eslint errors, build OK.

### AI Agents: "shows install card on first open, OK after Refresh" — 5th defect

Reproduced end-to-end (`tmp/mb-harness/details-race.mjs`): with relay connected
and target set, the page rendered "No default agent installed on this server"
and stayed there. Clicking Refresh fetched the real status and it appeared.

Root cause was NOT in `AIAgentsApp`. It was in the request dedup layer
(`src/utils/requestDedup.js`). Cache key was `${METHOD} ${URL}` only, so
two POSTs to the same endpoint with different bodies collided on the
in-flight slot:
1. `refreshInstances` fires first → `POST /api/agents/hermes {action:"instances"}`
   starts an in-flight request.
2. `loadDetails` fires ~ms later → `POST /api/agents/hermes {action:"details"}`
   sees the in-flight `instances` request, awaits it, gets the `instances`
   response back (no `installed` field).
3. `setDetails({success:true, instances:[...]})` → `details.installed` is
   undefined → install card shown.

Fix: include the request body in the cache key for non-GET methods. GETs
keep URL-only. Two new tests in `tests/requestDedup.test.mjs`:
"POSTs to the same URL with DIFFERENT bodies do NOT coalesce" (the
regression test) and "POSTs to the same URL with IDENTICAL bodies still
coalesce" (so we don't accidentally stop coalescing legitimate dupes).
Both mutation-tested. 410/410 tests pass.

Lesson: any in-flight coalescer keyed only on (method, URL) will silently
serve a wrong-shaped response to the second caller. Bodies carry intent
for POST/PUT/DELETE.

## Web UI tab stuck on "Opening Web UI…" (desktop + mobile)

Symptom: opening the agent Web UI claims a tab, writes a placeholder, and
never navigates it.

What I could prove (ground truth, not inference):
- Relay log ~/Library/Logs/ssh-monitor-relay.log shows gateways DID come up
  ("gateway live at http://127.0.0.1:18791", end-to-end check passed), so the
  relay tunnel is not the problem when it works.
- The relay's most recent webui:forward attempts fail with
  "connect ECONNREFUSED 127.0.0.1:<random>" and NEVER ack — and
  handleWebuiForward swallows its error, so the server waited 20s and then
  returned success:true with a GUESSED port. The browser was sent to a dead
  address.
- Chrome's Local Network Access (default-on since 142) blocks public-origin →
  loopback; the relay's existing mitigation answers a PNA OPTIONS preflight,
  but PNA was put on hold by Chrome and top-level navigations never preflight.
  So that mitigation is obsolete.
- Measured in real Chrome: an about:blank popup reports the OPENER's URL as
  location.href (about:blank inherits the creator URL), so the opener CANNOT
  detect "did the tab move?" — and after it moves, reading href throws. Both
  opener-side checks are blind. Do not reintroduce them.

Fix (app-side, no relay reinstall needed):
- The claimed tab now watches ITSELF: navigateWebUITab() writes a script into
  the tab that calls location.replace(direct), and if the document is still
  alive at the deadline renders a fallback card itself. Verified against real
  Chrome with the actual lifted code: live gateway → navigates, no card;
  never-commits → card + "Open through the server" works; dead port → Chrome
  error page (card cannot be shown, doc is already gone).
- Every failure path writes the reason INTO the tab (handleStartWebUI else +
  catch, openWebUIInTab tunnel failure, no-relay guard). Nothing is left on
  the spinner.
- New "Via server" button: same-origin /api/agents/webui-proxy, works from any
  device — the only route possible on a phone (its 127.0.0.1 is the phone).
- buildWebUIProxyUrl now emits the path-keyed form
  /api/agents/webui-proxy/m/<cid>/<port>?agent=<id> (was the query form, which
  breaks lazy chunks). It was dead code before this.
- Server: relay-start now returns 504 success:false when the relay never acks,
  instead of a guessed port.

422/422 tests (new tests/ai-agents-webui-open.test.mjs, 12 cases). Both key
assertions mutation-tested.

Follow-up worth doing: make handleWebuiForward send webui:fail so failures
surface in ~1s instead of the 20s ack timeout (needs a relay rebuild +
reinstall, which is why it was left out).

Q: "on mobile, select the relay installed on the Mac, Mac is on — does it work?"

## Web UI tab stuck on "Opening Web UI…" — part 2 (real fix) + Via server scoping

The 2026-09-09 fixes made every *known* failure path write into the claimed tab,
but the tab could STILL strand on the spinner forever: the self-watch fallback
card is only written AFTER `await callRef.current('webui-ctl','relay-start')`
resolves, and that POST has no deadline anywhere. Server legs have individual
timeouts (15s binPath + 10s secret + 20s relay ack), but `execCommand`'s
non-pooled path (src/app/api/server-backup/_ssh.js:319) can hang forever when an
SSH connect fires neither 'ready' nor 'error' — the fetch never settles, so
neither navigate nor failWebUITab ever runs.

Fix (src/apps/AIAgentsApp.js):
- Module-level `withDeadline(promise, ms, error)` — never rejects, resolves
  `{success:false, deadline:true, error}` on timeout, swallows late rejections.
- `WEBUI_OPEN_DEADLINE_MS = 75_000` (covers the ~45s worst-case server sum).
- Applied to the relay-start call in `openWebUIInTab` AND the start call in
  `handleStartWebUI` (it claims its own tab first) — on deadline the actionable
  fail card is written into the claimed tab. Verified: hung promise → deadline;
  late rejection swallowed; success/rejection pass through unchanged.

Via server button scoping (user request: only for loopback 127.0.0.1 on target):
- nanobot + hermes `details` actions now probe the Web UI listen address via
  `ss -tln` (netstat fallback) and return `webUIBind` + `webUILoopback`
  (loopback = 127.*, ::1, localhost; '[::]'/'0.0.0.0' are NOT loopback).
- AIAgentsApp renders the "Via server" button only when `details.webUILoopback`
  is true — the proxy dials 127.0.0.1:<port> ON the target over SSH, which only
  makes sense for a loopback-bound UI. Mobile auto-proxy and fail-card "Open
  through the server" rescue routes intentionally unchanged.
- Hermes gotcha: the DETAILS_SCRIPT is parsed by ===SECTION=== markers — the new
  probe needed its own `echo "===WEBUIBIND==="` marker AND the WEBUI section
  parser changed to `section('WEBUI','WEBUIBIND')`.

Validation: eslint 0 errors on all three files (6 pre-existing warnings);
full suite 425/425. awk/sed probe verified against 127.0.0.1 / 0.0.0.0 /
[::] sample ss output.

## Mobile recheck of the WebUI changes (same day)

Found + fixed one mobile inconsistency while re-verifying: the mobile branch of
openWebUIInTab ALWAYS opened the same-origin proxy — even when the new
webUILoopback probe says the UI is public-bound, contradicting the
Via-server-only-for-loopback rule and the hidden desktop button.

New mobile routing (mirrors the desktop rule):
- webUILoopback === false → phone goes DIRECT to http://<conn.host>:<webUIPort><bootstrapPath>
  (host resolved from connectionsRef via targetRef; NOT via the loopback proxy).
- loopback, or probe pending/unknown → same-origin proxy (previous behavior;
  safe default — a phone can never jump to the relay host's 127.0.0.1).
- webUILoopback === false but conn.host unresolvable → no URL is fabricated;
  falls through to the existing relay-required guard instead of silently proxying.

Safety properties kept:
- Route decision is fully SYNCHRONOUS (refs: detailsRef/targetRef/connectionsRef
  — NOT the render closure, which is stale after handleStartWebUI's loadDetails).
  openBlankWebUITab still runs in the same task as the click → popup not blocked.
- Tab is claimed only AFTER the URL is known, so the fall-through path never
  leaks a claimed spinner tab.
- withDeadline guards apply to Start Web UI on mobile too (the tab is claimed
  there before any mobile/desktop branch runs).

tests/ai-agents-webui-open.test.mjs: mobile test rewritten for the new contract
+ 2 new tests (deadline wrapping; Via-server loopback gating incl. ss/netstat
probe presence in both routes). Suite: 427/427. ESLint: 0 errors.
