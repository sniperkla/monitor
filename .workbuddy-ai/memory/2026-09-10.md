## Agent Web UI: in-app vs browser tab fork (AIAgentsApp)

Asked because "open in a new tab" was broken on phones in standard mobile mode
but appeared fine with desktop mode on.

Root cause of the mobile symptom: the external route depends on `window.open`,
which mobile Safari and iOS standalone/PWA refuse outright; requesting the
desktop site changes the UA, which flipped the `isMobileBrowser` heuristic and
made it *look* fixed.

Added:
- `src/utils/webuiOpenMode.js` — per-device preference
  (`localStorage['ssh_monitor_webui_open_mode']`) + `openExternalUrl()`
  (`window.open` → synthetic `<a target="_blank">` click fallback) +
  `isMobileLikeBrowser()`.
- `src/components/WebUIOpenChoiceModal.js` — bottom sheet on phones, centred
  card from `sm:`; two options, "Remember my choice on this device".
- `src/components/AgentWebUIView.js` — portal'd full-screen in-app view.
  Frames the SAME-ORIGIN proxy and **probes before mounting**, so a failure is
  a retryable card rather than the dead grey frame that got the old floating
  iframe removed. 44px targets + safe-area insets for mobile.
- `AIAgentsApp.js`: Open button is now a split control (action + caret that
  re-opens the chooser); label reflects the remembered mode. `handleStartWebUI`
  claims a tab only when the remembered mode is `external`. Both popup sites
  now go through `openExternalUrl`.
- `tests/ai-agents-webui-open-choice.test.mjs` — 11 new tests (438 total pass).

Verified: eslint 0 errors on all touched files; `next build` into
`tmp/.next-webui-choice3` compiled clean (output moved to /tmp/monitor-builds).

Key finding worth remembering: `/api/agents/webui-proxy` is **excluded from the
middleware matcher**, so its own `X-Frame-Options: SAMEORIGIN` +
`frame-ancestors 'self'` stand and same-origin framing is legal. App CSP's
`frame-src 'self'` also permits it.

Also done later in the same session: **Back now dismisses the in-app overlay**
(pushState + popstate, refs guarding against StrictMode double-invoke).

Then, on request ("can i drag or minimize for embed"): the in-app view became a
**floating window** — drag by the header, minimise to a bottom-right badge,
maximise/restore. Same portal, same probe-before-mount. Six header controls
wrap onto their own line on a phone so nothing overflows at 375px.

Two things that bit and are worth remembering:
- Drag must use **pointer** events. The live-log panel's
  `mousedown`/`mousemove`/`mouseup` trio is mouse-only and does nothing on
  touch; it also needs `touch-action: none` on the handle or the page scrolls
  instead.
- The iframe must go `pointer-events: none` during the drag, or it swallows
  the pointer stream and the panel jumps and sticks.

Then ("i want can resize and can attach on left or right pane"): added **resize**
(right edge, bottom edge, bottom-right corner) and **docking** to the left or
right as a full-height pane. While dragging, a translucent hint appears once the
pointer is within ~12% of an edge (clamped 72–160px) and the dock commits on
release. Docked panes resize from their inner edge only. Header gained
attach/detach buttons; both are hidden below 768px. Docking preserves the
floating box, so detaching restores the previous layout. Note: the docked pane
**overlays** the desktop rather than reflowing it — reflowing would require
teaching `DesktopEnvironment` about a panel it does not own.

## Hermes embed navigation regression (14:07)

Rechecked the "Hermes chat navigation works in a new tab but not embedded"
report. Root cause: the proxy already patched `history.pushState` and
`replaceState`, but a real Hermes `<a href="/chat/<id>">` click bypasses both.
Inside the same-origin iframe, that bare navigation hits the monitor's own root
and 404s; in the external Local Relay tab the remote Web UI owns `/chat`, so it
works.

Fixes:
- Injected proxy script now capture-intercepts ordinary left-click same-origin
  links and runs `containInTunnel(href)` before navigation; modifier clicks and
  `_blank`/other target links remain untouched.
- `AgentWebUIView` watches its same-origin frame. If Hermes still escapes to a
  monitor-root path, it records the path, reconstructs the path-keyed tunnel URL,
  reloads the frame in-place, and shows a small diagnostic notice. The retry
  cooldown prevents judging the repaired frame while it is loading.
- Added regression tests in `tests/webui-proxy-assets.test.mjs` and
  `tests/ai-agents-webui-open-choice.test.mjs`.

Verified 452/452 tests pass, touched-file eslint clean, and build compiled into
`tmp/.next-webui-choice9` (moved out to `/tmp/monitor-builds`).

## Screenshot follow-up (14:54)

User still saw only a dark-green Hermes shell after entering Chat in the embed;
external tab worked. Re-checked upstream Hermes Web UI: it uses **Vue Router

## StrictMode trap worth remembering

Next 16 defaults `reactStrictMode` to true, so every effect runs
mount → unmount → mount in dev. A `pushState` in an effect plus a
`history.back()` in its cleanup **fights itself**: the simulated unmount pops
the entry the remount just pushed, popstate fires, and the overlay closes
itself the instant it opens. Guard the push with a ref; pop in a separate
effect keyed on `open`.
