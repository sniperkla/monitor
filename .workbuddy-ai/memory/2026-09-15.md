## OpenClaw embedded Web UI: "auto-added Gateway secret" was a stale seed (fixed)

**Report:** on the AI Agents Web UI embedded in openclaw, the Gateway secret is auto-added
but Connect fails with `unauthorized: gateway token mismatch`. Context given by x: a fresh
`openclaw` install.

**Root cause (two halves, both measured, not inferred):**

1. A fresh OpenClaw install ships with **no gateway credential at all** on `fc-fedora40`:
   `~/.openclaw/openclaw.json` was `{"gateway":{"mode":"local","bind":"loopback"}}`,
   `openclaw dashboard --json` → `"tokenIncluded": false`, and

   `openclaw doctor --generate-gateway-token`, restart the Gateway, then try again."*

`{token, password}` → the exact reported error string. Confirmed the Control UI does **not**
pre-fill from localStorage (drove the login form, reloaded, field stayed empty) — so the
value can only come from that sessionStorage key.

## OpenClaw Reconfigure: `base64: invalid input` (fixed)

**Report:** "Starting Reconfigure OpenClaw... → `$ write ~/.openclaw/.env` → `base64: invalid input`".

**Root cause — a JS string-quoting bug, not SSH:** `src/app/api/agents/openclaw/route.js:1002`
built the command as

```js
`export OC_HOME="${HH}"` + '; echo \'${envPyB64}\' | base64 -d | python3'
```

The second half is a **single-quoted** JS string, so `${envPyB64}` was never interpolated. The
remote ran `echo '${envPyB64}' | base64 -d` → the literal text reached `base64` → "invalid
input". python never ran, `ENV_UPDATED` never printed, and reconfigure aborted before the
gateway restart. Only this one line was affected; zeroclaw:1020 and everything else use real
template literals.

**Fix:** one template literal
(`` `export OC_HOME="${HH}"; echo '${envPyB64}' | base64 -d | python3 2>&1` ``) plus a
diagnostic tail (last 3 lines of stdout/stderr) in the failure message so the next failure
names itself.

**New test `tests/openclaw-reconfigure-env.test.mjs`** — lifts the real command expression out
of the route, evaluates it with `new Function('HH','envPyB64', …)` (so an uninterpolated
placeholder is *visible*, not just pattern-matched), then actually runs it under `sh -c`
against a temp `OC_HOME`. Proven to fail against the old line and pass against the new one.
Also pins that no agent route concatenates an uninterpolated `${…}` in a quoted string.

`npm test` 622 pass / 0 fail; eslint clean. **Not deployed.**

**Lesson (generalises):** when building a shell command in a template literal, a `+ '…'`
splice into a quoted string is invisible in review and fails only at the remote. Grep for
`+ *['"][^'"]*\$\{[a-zA-Z_]` across `src/app/api/agents/*/route.js` after any edit there.

**Verified live on fc-fedora40 (two harnesses, both PASS):**

- `scratch/verify-oc-reconfigure-cmd.mjs` — renders the shipped command out of the route and
  runs it over SSH against a throwaway `OC_HOME=/tmp/oc-reconf-verify`. Result: `ENV_UPDATED`,
  `KEEP_ME` preserved, `base64==value` intact, mode `600`, `python3`/`base64` both at
  `/usr/bin`. Nothing on the box touched.
- `scratch/verify-oc-reconfigure-e2e.mjs` — the real user flow, `POST action=reconfigure`
  through the dev server with an **existing** key set to its **current** value (semantic
  no-op; snapshots `.env` and diffs afterwards). `success=true restarted=true`,
  log = `$ write ~/.openclaw/.env / ENV_UPDATED`, `.env` **byte-identical** afterwards, key
  present exactly once. Gateway confirmed up on 18789 after the restart (`webui-ctl status`).

Dev server was restarted before the e2e run (stale compiled route would have made the result
meaningless). **Still not deployed to prod.**

## In-app browser: two rendering failures, both reproduced (not yet fixed)

Asked: "recheck why localhost:3076 on fedora40 is blank, and monitor.eaqdragon.com in the browser
app is stuck on the connecting indicator". Both reproduced in Chrome
(`scratch/browserapp-frame-repro.mjs`, `scratch/probe-relay-boot-diff.mjs`,
`scratch/bisect-relay-bridge.mjs`). **Neither is fixed — diagnosis only.**

### 1. `localhost:3076` blank — Vite dev app dies on nested module imports

A localhost:PORT address-bar entry with a connection selected becomes a **`type:'webui'`**
"Local Service" tab → `/api/agents/webui-proxy/m2/<conn>/3076/` (sub-path tunnel proxy).
3076 on fc-fedora40 is a **Vite dev server** ("Playground — Immersive Code Editor").

- Document 200, entry chunk 200, BUT every *nested* import 404s at the monitor origin:
  `/@react-refresh`, `/node_modules/.vite/deps/react.js`, `/src/App.tsx`, `/src/index.css`,
  `/node_modules/vite/dist/client/env.mjs`.
- Cause: the proxy rewrites URLs in **markup** only. Vite's chunks contain root-absolute
  module specifiers (`import "/node_modules/vite/dist/client/env.mjs"`) which resolve against
  the document ORIGIN, not the proxy sub-path. There is no `<base>` (and a `<base>` would not
  help — root-absolute refs ignore the base path).
- Precedent for a fix: `rewriteRootAssetRefs()` already rewrites `assets/` and `/assets/` refs
  inside JS bundles for Hermes. Extending it to Vite-dev shapes (`/@vite/`, `/@react-refresh/`,
  `/node_modules/`, `/src/`) is the contained option; an un-prefixed tunnel fallback keyed by
  Referer/coord cookie is the general one (but needs a root catch-all — invasive).

### 2. `monitor.eaqdragon.com` "CONNECTING…" — the relay's injected bridge breaks Next

- Document 200, all chunks 200 and **byte-identical to prod** (md5), no console errors, no CSP
  violations, no pending requests — yet `window.next` is **undefined**: the Turbopack runtime
  never initialises, so `useSession()` stays `loading` and `page.client.js` renders its
  SSR "CONNECTING..." forever (no `/api/auth/session` is ever requested).
- Loaded **directly**, the same prod page boots fine. Bisecting the relay's injected script:
  removing the block that overrides the `src`/`href` **property setters**
  (`HTMLScriptElement.src, HTMLLinkElement.href, HTMLImageElement.src, …`) restores boot
  (`window.next = object`). Removing any other patch changes nothing.
- Mechanism: the static `<script src="/_next/...">` tags are root-absolute (they ignore the
  injected `<base>`), while Next's *dynamically inserted* scripts go through the patched setter,
  which rewrites them to `/p/<enc>/_next/...`. Every chunk is therefore fetched AND executed
  **twice under two URLs** (17 resources direct vs 34 through the relay) → two Turbopack module
  instances → dead app. Same class of bug as the documented webui-proxy ASSET_KEY split.
- Fix belongs in `public/local-relay.js` (mpRewrite should NOT re-prefix a same-origin
  root-absolute path that the relay's own un-prefixed fallback already serves), so it needs
  `scripts/build-relay.mjs` + replace `~/.ssh-monitor-relay/local-relay.js` + `launchctl kickstart`
  — and re-pinning `relay-install-audit.mjs`.

## ROOT CAUSE FOUND: monitor.eaqdragon.com in-app (the "CONNECTING…" hang)

**The bridge, not the HTML rewriting.** `mpRewrite` in the injected bridge wrapped
**same-origin root-absolute** URLs in the current `/p/<enc>/` prefix. Its stated reason
was that the un-prefixed repair once answered with a **302** and COEP refuses a script
behind a redirect — but the repair was later changed to **re-dispatch internally**
(`req.url = back; return handleWebProxyHttp(…)`), so the browser sees one plain 200 and
no prefix is needed. Nobody revisited the bridge when the repair changed.

The damage: the parser loads `<script src="/_next/…">` **bare**, and the bridge then
re-points the *same element* at the prefixed spelling (src setters → `setAttribute` →
the `MutationObserver` safety net `__mpFixNode`). All 17 chunks load twice under two
URLs; the browser holds **two module instances of each**; `window.next` is never
defined; the session hook never leaves `loading`; the page sits on "CONNECTING…"
forever with every asset returning 200. It also surfaces as `net::ERR_ABORTED` —
re-setting `src` cancels the in-flight bare load.

**Fix (shipped):**
1. `mpRewrite` returns a same-origin URL untouched. Cross-origin still wrapped (that
   branch is the CORS/hotlink-referer fix and earns its keep).
2. The two HTML passes that prefixed root-absolute refs (tags + `/_next/` strings in
   inline scripts) are **deleted**. Rule: *a root-absolute URL is never rewritten,
   anywhere.*

Measured through the real relay on our own dashboard:

| | requests | API calls | `window.next` |
|---|---|---|---|
| before | 49 | 0 | `undefined` |
| after | 37 | 4 | `object` |

After: renders "SSH Monitor … monitor@orbit — ssh — 80×24", 17 distinct chunks, **no
chunk fetched twice**, 4 API calls (`auth/session`, `health`, `csrf`, `connections`).
speedtest.net shows the Cloudflare banner. Shipped: rebuilt `local-relay.min.js`
(237034 B), re-pinned the audit (reason 9 marked SUPERSEDED, reason 11 added),
installed, kickstarted, no drift. `npm test` **640/640**, eslint clean.

**What I got wrong, and the two lessons worth keeping:**

- I spent most of a session on a **local mirror** that served the target's HTML and
  proxied every path but had **no bridge, no `<base>`, no repair**. It reported
  "un-prefixed boots, prefixed never boots" — an artefact: the harness was simulating
  the bridge's rewrite by hand. The decisive test was two copies of
  `public/local-relay.js` **itself**, differing only in that one branch
  (`scratch/relay-prefix-real.mjs`), against the real target. A mirror is not the product.
- **Ask the browser who requested the URL.** `request.initiator()` named the culprit in
  one run (`Element.setAttribute <- __mpFixNode`) after several rounds of reasoning about
  the module graph had produced only plausible stories.

**Still open:** a single React error #418 (hydration mismatch) appears through the relay
and not on direct load. The app boots and renders anyway, so it is cosmetic for now —
worth chasing only if a visible flash is reported. Likely inherent to sub-path proxying:
the client sees `location.pathname === '/p/<enc>/'` while the server rendered `/`.

That is the IDE's `node-safe-delete` shim intercepting Next's end-of-build `fs.unlink`;

**The deploy is git-based, so nothing in this working tree can ship.**

```
site A  → origin=http://127.0.0.1:18780  localStorage keys=["__probe_secret"]
site B  → origin=http://127.0.0.1:18780  localStorage keys=["__probe_secret"]
VERDICT: ✗ NOT ISOLATED — site B can read site A's storage
response: <socket closed with NO response>
VERDICT: ✗ upgrade refused — any site using WebSockets is dead
```

Chose the fix the user picked — one origin per site — then hit a constraint that changed
its shape: **`ifconfig lo0` on macOS carries only `127.0.0.1`**, so binding any other
`127.x.y.z` fails with `EADDRNOTAVAIL` unless someone runs `sudo ifconfig lo0 alias …`
first (root, and gone after a reboot). So the origin differs by **PORT**, which needs no
privileges and is already how this proxy re-binds when 18780 is taken.

Implemented:

- Each target origin gets its **own loopback listener**, hence its own origin, hence its
  own storage. Chromium partitions storage for us with no code of ours involved.
- A site is therefore served at its **own ROOT** — no `/p/<enc>/` prefix in the document
  URL. That makes the module-graph split *structurally impossible* rather than merely
  fixed: there is only one spelling a chunk can have.
- Entry listener gains `/go/<enc>/…` → **307** to the site's origin. `/p/<enc>/…` stays
  and still serves the target, so a deployed app that predates `/go/` keeps working; it is
  the shared-origin path and is marked deprecated.
- A document that redirects **cross-origin** is 307'd to that origin's own listener, never
  served here wearing the wrong origin. Documents only — a subresource behind a redirect is
  refused outright under COEP.
- The bridge now reports the document's **real URL** (`data.target`), because a bare
  loopback origin is not invertible. Without it the omnibox stops tracking any SPA.
- Origin→port map persists to `~/.ssh-monitor-relay-origins.json` and is re-bound eagerly,
  because the port IS the origin and a new port means a silent logout.
- **WebSocket upgrades are tunnelled** instead of refused. Absolute `ws(s)://` becomes
  `ws://<listener>/__ws/<b64(scheme//host)>/…` (the scheme travels so TLS still happens
  upstream); a relative one needs nothing.

### Four bugs I wrote and had to measure my way out of

1. `setTimeout(bind, 0).then(resolve, reject)` — `setTimeout` returns a Timeout, not a
   promise, so the port-retry path threw inside a socket error handler and the **second**
   site to be opened hung forever with nothing in the log.
2. The tunnel leaked a **socket pair per WebSocket**. An HTTP-server socket is half-open, so
   a peer that just goes away delivers `end` and never `close`. Teardown now handles both.
3. Teardown also held the upstream socket as an *argument*, but the client side usually goes
   first — so teardown ran before `upgrade` had handed it over, marked the tunnel clean and
   left the socket open. It is a closure variable now.
4. Watching an upgraded `ClientRequest` for `close` tears the tunnel down immediately after
   the 101: that event fires when the *request* finishes, which is the moment the upgrade
   succeeded. The handshake arrived and every byte after it vanished.

Found by `scratch/relay-handle-probe.mjs`, which uses `process.on('beforeExit')` as the only
honest signal. My first version called `process.exit(0)` and therefore proved nothing.

### A real cross-site channel the per-site origins do NOT close

`Cookie: mp_proxy_target=…` was measured arriving on a **different** site's origin. Cookies
are scoped to a HOST and know nothing about ports, while an origin includes the port — so a
cookie set on any per-site origin is sent to every per-site origin. The hint cookie is now
set only on the deprecated `/p/` path, where the un-prefixed repair actually reads it; a
per-site listener sets no cookie at all. Pinned by two tests.

Also: the eviction cap counted *map* entries, but an evicted origin keeps its entry (its
port is its identity) with `server: null`, so the map never shrinks — the guard either never
fired or closed everything. It counts live listeners now, and eager re-binding is bounded at
24 rather than every origin ever browsed.

### The relay was dead, and it was not my change

plist's `ProgramArguments[0]` was `~/.hermes/node/bin/node`, which **no longer exists** — so
the relay had been down with no symptom, because a dead relay writes nothing to its log. Two
traps in the repair: use `plutil -replace ProgramArguments -json '[...]'` for the whole
array, since `-replace ProgramArguments.0` **inserts** and leaves a stray argument that makes
node try to run the old path as a script. Backed the plist up to
`/tmp/com.ssh-monitor.relay.plist.bak`; repointed at `/opt/homebrew/bin/node`; re-bootstrapped.

## The one unverified link — and the leak it exposed (2026-09-15, later)

Everything *below* the UI was already green (relay unit tests, real-Chrome relay probes,
build/install/audit). The link still unverified was **the app UI driving the relay** — the
`/go/` hop as the user actually experiences it. Driving it found a real bug.

### Driving the real UI with no stubs at all

`scratch/webui-app-go-hop.mjs`. The trick that removed every stub: mint the session with
`sub` = **the paired relay owner's `googleId`** (`103964071993904442031`), found by reading the
local Mongo `systemsettings` doc keyed `relay_tokens` and resolving it against `users`. Then
`GET /api/relay/token` returns the LIVE relay (`connected: true`, `webProxyPort: 18780`) and
that user's real `vault.isConfigured` + `supporter.status` rows pass their gates. The only
client-side setup left is the vault **unlock** cache (`sessionStorage._vault_uri`), which the
app itself writes on a normal unlock. **16/16 checks.**

Two harness traps worth remembering:

* the desktop icon's `[data-icon-id]` rect is **not trustworthy** — it is `position:absolute`
  with a pointer-drag handler, and its rect was observed duplicated across icons. Use the
  label span, `scrollIntoView` first (it sits below the fold at 1000px), and re-measure
  immediately before clicking.
* "did the link move the frame to a *different* frame" **can never pass**: the `Frame` object
  you hold is the one that navigated, so its `url()` has already changed. Compare **origins**.

### The leak: a cross-origin link kept the linker's origin

Clicking example.com's link to iana.org left the frame on
`http://127.0.0.1:18800/p/aHR0cHM6Ly9pYW5hLm9yZw/domains/example` — the **same origin as
example.com** — and `localStorage.getItem('__probe_site')` returned `"A"`. iana.org read
example.com's storage. That is the exact leak one-origin-per-site exists to prevent, on the
most common navigation there is.

Mechanism — a collision between two features that were each right on their own. `mpRewrite`
turns an absolute cross-origin URL into `/p/<enc>/…` on the current listener, and
`__mpFixNode`'s MutationObserver applies that to **every** element carrying an `href`,
including `<a>`. The click interceptor then bails at
`if(u.origin===location.origin)return`, so the parent is never told, and the site listener's
`/p/` branch serves the destination in place.

Fix, in `handleWebProxyHttp`: that branch now 307s a cross-origin **document** to
`ensureSiteListener(target.origin)` and leaves subresources alone. The discriminator is the
INCOMING `sec-fetch-dest` (`document`/`iframe`/`frame`) — the browser stating what it will do
with the response. Redirecting a subresource would be refused outright under COEP, so an
absent header keeps the old in-place behaviour rather than guessing: a broken asset is worse
than the leak. (Safari before 16.4 sends no `sec-fetch-*`, so it keeps the old behaviour.)

After the fix the frame lands on `127.0.0.1:18818/help/` — iana.org's **own** listener — the
key reads `null`, and the omnibox still reports `http://www.iana.org/help/` via `data.target`.

Also settled: the `127.0.0.1:48923` CORS noise in the console is the relay's **discovery**
listener, not a bug.
