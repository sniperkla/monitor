## Follow-up: Stop button (same session)

nanobot had. Closed it:

## Correction: the relay does NOT self-update
An earlier note claimed "the relay self-updates by re-fetching /local-relay.js". **False for the
current `public/local-relay.js`** — the only `fetch()` calls are the pairing endpoints. There is no
update mechanism at all.
Consequence for the npm route: `ensureInstalledScript()` is called **once**, inside
`if (args.install || args.pair)` (line 338). The service runs `~/.ssh-monitor-relay/local-relay.js`,
a copy made at install time. So `npm update -g ssh-monitor-relay` replaces the npm copy but does
**not** refresh the running service — the user must re-run `local-relay --pair`. The curl route
sidesteps this by re-downloading current bytes on every install.

## npm publish trap, worse than the propagation lag: 1.0.2 is dead (E409 staged phantom)
`npm publish` printed `+ ssh-monitor-relay@1.0.2`, **exit 0**, log showed `http fetch PUT 202`
(202 Accepted, NOT the usual 201) + "Your package is being processed". 100 min later the
packument still listed only 1.0.0/1.0.1, `time.modified` unchanged, tarball 404, no incident on
status.npmjs.org. Retrying → `E409 Cannot publish over previously staged version "1.0.2"`, while
`npm stage list` says "No staged packages found" — so there is no stage-id to reject.
Known npm bug: https://github.com/npm/cli/issues/9889 (same signature).
**1.0.2 is permanently unusable; 1.0.3 carried identical bytes and landed in ~3 min.**
Rules: (1) a 202 is not a publish — always verify by fetching the tarball and hashing it;
(2) never bump the next version until the current one is confirmed live, or you can't tell
"lag" from "wedged". The tell for the bug is **E409 on retry + unchanged `time.modified`**.
Don't confuse it with real lag: 1.0.3's packument updated ~3 min in while the tarball still
404'd — packument first, tarball after.

## F8 (user-reported): `--pair` printed no code on an already-paired machine — FIXED
"no key appear after installed via npm or direct when success and need to remove first when
install again". Both halves are one bug, on BOTH routes (shared block).

**Safe repro trick: pairing blocks BEFORE installMacOS(), so killing during the approval
wait exercises the bug and changes nothing** (verified config token unchanged after).

com.ssh-monitor.relay job.
