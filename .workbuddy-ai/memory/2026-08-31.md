## BUG FIXED: relay install succeeds but SSH list never refetches (~00:50)
User report: "when i install local relay success it's not auto fetch ssh connection".

### Mechanism (verified by direct read, not just subagent)
`AppContext.js:453-464` is the ONLY auto-refetch trigger — a `window` listener for
`ssh-mode-changed`, guarded at `:457` by
`if (prevModeRef.current === curMode) return;` where curMode is
`` `${ssh_monitor_ssh_mode}:${ssh_monitor_preferred_relay}` ``.

`SettingsApp.js` install-success effect (~:1290) did:
```
1300  localStorage.setItem('ssh_monitor_ssh_mode', 'local');
1301  window.dispatchEvent(new Event('ssh-mode-changed'));  // <-- fetch fires HERE
1305  localStorage.setItem('ssh_monitor_preferred_relay', relayName);  // too late
```
Two defects:
1. **Suppression.** `dispatchEvent` is synchronous, so the listener ran at 1301.
   `ssh_monitor_ssh_mode` is STICKY — `AppContext.js:540-543` sets it to 'local'
   on any mount where a relay is up, and it is never cleared. So on a re-install
   the composed string is unchanged → guard returns → **no refetch at all**.
2. **Ordering.** Even when the guard passed, the request at 1301 carried the OLD
   (or absent) `x-preferred-relay`. `/api/connections` → `getDynamicConnection`
   (`src/lib/mongodb.js:190`, keys on `x-preferred-relay` at `:95`/`:108`) needs
   that header to route localhost DBs, and it is exactly what flips
   `{data:[], relayRequired:true}` into real rows. The 1305 write dispatched
   nothing, so no second fetch ever corrected it.

### Fix applied (SettingsApp.js)
- Moved the `ssh_monitor_preferred_relay` write + `setPreferredRelay` ABOVE the
  mode switch, so both keys are set before anything can fetch.
- Replaced reliance on the event with a direct `fetchConnections()` call
  (`fetchConnections` is destructured from `useApp()` at :231). `dispatchEvent`
  kept for other listeners; if it also fetches, `dedupedFetch` coalesces.
- Added `fetchConnections` to that effect's dep array (safe: guarded by
  `!relayInstallSuccess`, which flips true on first success).
- Same bug on the teardown paths — `handleDisconnectRelay` (:1372) and
  `handleRevokeAllRelays` (:1387) removed the preferred relay with NO dispatch
  and NO refetch. Added `fetchConnections()` to both.

### Deliberately NOT changed
The `prevModeRef` guard in AppContext must stay: `fetchConnections` dispatches
`ssh-mode-changed` itself at `:346`/`:369` (relay-required / DB-error auto-switch
to 'server'), so removing the guard reintroduces a fetch loop. Fix at the call
site, not in the shared listener.

## BUG FIXED: Hermes OpenRouter key dropped on one-click / fresh install; spawned gateway booted without credentials (~16:47)
- Root cause: `src/app/api/agents/hermes/route.js` serialized the install env payload without a final newline while its `upsert_env` loop used plain `read`. POSIX `read` ignores an unterminated final record, so a one-key payload (`OPENROUTER_API_KEY`) persisted no key; multiple-key payloads lost their final key.
- Fix: payload now adds a terminating newline and the shell loop defensively uses `read -r line || [ -n "$line" ]`. `.env` remains mode `0600`.
- Spawn flow: newly spawned Hermes homes intentionally keep an isolated empty `.env`, but previously started the gateway before the wizard could collect a provider key/token. Spawn now returns `needsConfiguration: true` and does not start; Save & Start persists credentials first.
- Runtime start: both tagged systemd units and nohup fallback now source/load the instance `.env`, so an OpenRouter key written by reconfigure/install reaches the gateway. Status probing uses the tagged home rather than default paths.
- Fixed wizard request callback dependencies to include `instance`, preventing stale closure requests from targeting the default instance after switching to a spawned one.
- Added static regression checks in `tests/multi-instance.test.mjs` for final-line merge, no pre-config spawn start, and instance `.env` loading. **Not runtime-verified:** Bash/Node/NPM remain unusable under the WorkBuddy sandbox (exit 127); test and lint commands could not start.
