# 2026-09-05

## Fixed: nanobot WebUI `401 Unauthorized` on `/api/settings` (relay stripped auth header)

**Symptom:** nanobot WebUI loaded fine at http://127.0.0.1:18790, but every `/api/settings`
call returned `401 Unauthorized` → "Could not load settings".

**Root cause** — NOT a nanobot/gateway problem. The Local Relay was deleting the
`Authorization` header before forwarding to the gateway:

```
// public/local-relay.js  handleWebuiHttp()
const headers = { ...req.headers, host: `127.0.0.1:${gw.remotePort}` };
delete headers.cookie; delete headers.authorization;   // ← the bug
```

The nanobot SPA mints an `api_token` from `GET /webui/bootstrap` (auth'd by the
bootstrap secret via `X-Nanobot-Auth`) and then sends it as
`Authorization: Bearer nbwt_…` on every `/api/*` call. With the header stripped the
gateway sees no credentials → 401.

**Proof:** through the tunnel, `?token=<api_token>` → 200 but
`Authorization: Bearer <api_token>` → 401, for a freshly minted token.

**Fix:** `public/local-relay.js` — keep `delete headers.cookie` (the browser shares one
cookie jar across all 127.0.0.1 ports, so the monitor session cookie must not leak to
the gateway) but stop deleting `authorization`. Added an explanatory comment.
Copied to `~/.ssh-monitor-relay/local-relay.js` (backup at `local-relay.js.preauthfix`),
restarted with `launchctl kickstart -k gui/$(id -u)/com.ssh-monitor.relay`.

### nanobot WebUI / relay facts worth keeping
- The WebUI tunnel is **in-memory only** in the relay (`webuiGateways`), and the monitor
  server only sends `webui:forward` on demand (`src/app/api/agents/nanobot/route.js`,
  action `webui-ctl` / op `relay-start`). **Restarting the relay kills the tunnel** — the
  user must click "Start Web UI" again. There is no auto re-push on relay reconnect.
- Relay is a launchd agent: `~/Library/LaunchAgents/com.ssh-monitor.relay.plist`
  (RunAtLoad + KeepAlive, logs to `~/Library/Logs/ssh-monitor-relay.log`).
- Local port 18790 auto-increments on EADDRINUSE (`gw.port += 1`), so a stale relay can
  silently put the gateway on 18791.
- Auth flow: SPA reads the bootstrap secret from the URL hash first, then localStorage
  key `nanobot-webui.bootstrap-secret` (`G8() || H8()`). The relay injects the secret into
  the served HTML for this reason. Secret → `GET /webui/bootstrap` → `api_token` →
  `Authorization: Bearer` on REST, `?token=` on the WebSocket.
- `/opt/homebrew/bin/nanobot` is broken (`No module named 'nanobot.cli'`); the pipx one at
  `~/.local/bin/nanobot` is a *different* package (ROS-style robot nodes, no `webui`
  command). The real gateway runs on the remote SSH target, not locally.

### Added
- `scratch/verify-nanobot-webui-auth.sh [port]` — end-to-end auth check
  (root → injected secret → bootstrap token → `Bearer` on `/api/settings`).

### Embedded browser (`AIAgentsApp.js` floating window) — ERR_CONNECTION_REFUSED recovery
- If the floating window is opened **before** the relay tunnel is ready (or while
  the SSH tunnel from `webui-ctl` is still being established), the iframe hits
  `127.0.0.1 refused to connect` and stays in that state — the iframe's
  `key` (`${target}-${details.webUIPort}-${webUIPath}`) doesn't change, so it
  does NOT auto-retry. The user must click the **refresh button** (circular
  arrow in the floating window's address-bar toolbar) or close + reopen the
  window. The **external-link button** (top-right) opens the WebUI in a real
  browser tab as a guaranteed-good fallback.
- **Address-bar bug** in `src/apps/AIAgentsApp.js:3501`: typing `http://...`
  into the floating window's address bar prepended `/`, so
  `http://127.0.0.1:18790/...` became `/http://127.0.0.1:18790/...` and the
  iframe loaded the central proxy with that bogus path. Fix: detect
  `^https?://` and use absolute URLs as-is; everything else is treated as a
  proxy path.

### ROOT CAUSE of "can't access ANY webUI" — stale min bundle bricking the relay
- `server.js:509` serves `/local-relay.js` preferring `public/local-relay.min.js` when
  it exists. That min file was **Sep 2**, i.e. predates the whole WebUI gateway feature.
- The relay **self-updates** by re-fetching `/local-relay.js`. So every relay restart /
  re-pair made it **silently downgrade itself to a bundle with zero `webui` support**
  (`grep -c webui` = 0, no `webui:forward` handler, no `webuiGateways`) → port 18790
  could never open, no matter how many times the user clicked Start Web UI.
- md5 proof: installed relay == `public/local-relay.min.js` (`c0e31bf4…`);
  fresh source `public/local-relay.js` = `8afea6a8…`.
- **Fix:** renamed `public/local-relay.min.js` → `public/local-relay.min.js.stale-sep2`
  (quarantine, not delete). `server.js` falls through to the source on the next request —
  **no server restart needed**, the `fs.existsSync` check is per-request.
  Then redeployed source → `~/.ssh-monitor-relay/local-relay.js`
  (dead bundle kept at `local-relay.js.dead-sep2min`) and `launchctl kickstart -k`.
- **Rule for the future: never let a minified/bundled artifact take precedence over the
  maintained source.** If a `.min.js` is ever regenerated, it must be rebuilt from the
  CURRENT source, and its mtime must be newer than the source's.

### Diagnostic trick worth reusing
`md5 -q` the installed relay (`~/.ssh-monitor-relay/local-relay.js`) against each candidate
in `public/`, plus `grep -ci webui` on each. Instantly tells you which bundle is live and
whether it has the feature you're debugging.

### Follow-up (not done)
- `server.js:509` still prefers `local-relay.min.js` in principle — the code path is
  unguarded, so recreating a stale `.min.js` will reintroduce this bug. Change it to
  prefer the source (or compare mtimes). Requires restarting the dev server to pick up.
- No auto re-push of `webui:forward` when a relay reconnects — the tunnel stays dead until
  the user clicks Start Web UI again. Server-side fix would be to re-push on relay connect.

## Embedded browser REMOVED — Web UI now opens in a real tab (user's call)

**User's reasoning (agreed with it):** the Local Relay must be installed locally anyway, so
embedding bought no isolation — only failure modes. Direct URL
`http://127.0.0.1:18790/#/?bootstrapSecret=…` already worked fine in a real browser.

**Replaced in `src/apps/AIAgentsApp.js`:**
- `openWebUIBrowser()` + `retryWebUI()` → **`openWebUIInTab(overridePath, preopenedTab)`**.
- Deleted the whole floating panel JSX (~200 lines) and its state: `webUIOpen`,
  `webUIMinimized/Maximized/Pos`, `webUIPath`, `webUIAddrInput`, `webUILoading`,
  `webUIHistory/HistIdx`, `webUIReady`, `webUITransport`, `webUIRetryNonce`,
  `webUILoadingSlow`, `webUIRef`, `webUIIframeRef`, drag refs + `handleWebUIDragStart`,
  and the loading-timers `useEffect`. Removed now-dead imports `RotateCcw`, `AlertTriangle`.
- Kept: `probeReachable` / `waitUntilReachable` (still used to prove the tunnel),
  `startingWebUI`, `handleStartWebUIRef` (START_WEBUI postMessage).
- Buttons: "Web UI" (action row) and "Open in New Tab" (quick-launch card) both call
  `openWebUIInTab()`.

**Popup-blocker gotcha (the subtle part):** `window.open()` only escapes the blocker when
called **synchronously** in the click handler; after an `await` the user-gesture token is
gone. So `handleStartWebUI` claims a blank tab up front via `openBlankWebUITab()` and
passes it into `openWebUIInTab` to navigate once the gateway is up. Also: do NOT put
`noopener` in the features string — it nulls the handle needed to navigate later; set
`tab.opener = null` manually instead.

## Web UI card UX rework (user request)

Four changes, all in the Web UI quick-launch card unless noted:

1. **"Start Web UI" now reflects real state** — shows a green `✓ Running` pill when the
   Web UI is up, `⚡ Start Web UI` (amber) when stopped, `Starting…` spinner in flight.

3. **Removed the pulsing "running" status pill** — the button carries the state now.
4. **Removed the `Web UI` button from the action row** next to Uninstall/Reconfigure
   (that row is destructive actions only). `Globe` import dropped with it.

### New API field: `details.webUIActive` (nanobot route, `action: 'details'`)
- **Do NOT reuse `details.running` for Web UI state.** `running` is the *gateway* process;
  `nanobot webui` is a SEPARATE process on `webUIPort`. Using `running` would show
  "Running" when the Web UI is actually down — and disable the very button that would
  fix it.
- Added a live port probe: `curl -o /dev/null -w "%{http_code}" --max-time 2
  http://127.0.0.1:<webUIPort>/` → `webUIActive = hc >= 200 && hc < 500`.
  Costs one extra SSH round-trip (≤2s) per details load.
- Chose a port probe over `pgrep -f '[n]anobot.*webui'`: the webui-ctl handler has to
  filter out its own shell's argv via `$$`/`$PPID`, which is fragile to layer into the
  much bigger details script.
